"모델이 클수록 똑똑하다." 지난 몇 년간 이건 거의 법칙이었다. 그런데 2026년 6월, 노트북 한 대에 들어가는 작은 모델이 자기보다 훨씬 큰 모델과 비슷한 점수를 냈다. 점수만 보고 믿기엔 미심쩍어서, 직접 맥북에 받아 돌려봤다.

무엇이 공개됐나

2026년 6월 17일, 중국 Weibo의 AI 연구진이 신규 LLM 모델 VibeThinker-3B를 공개했다(기술 리포트는 하루 전인 16일자). 한 줄로 요약하면 이렇다.

30억 파라미터짜리 작은 모델이, 훨씬 큰 프런티어 모델과 비슷한 점수를 냈다.

 

이름의 "3B"가 그 크기를 가리킨다. B는 billion(10억), 3B는 파라미터 30억 개라는 뜻이다. 파라미터는 모델의 덩치를 나타내는 숫자인데, 요즘 최상위 모델이 수천억~조 단위인 걸 생각하면 3B는 한참 작은 축이다. 즉 VibeThinker-3B는 "파라미터 30억 개짜리 소형 모델"이라는 이름이다.

 

첫째, 처음부터 새로 만들지 않았다. Opus나 GPT 같은 모델은 막대한 비용을 들여 밑바닥부터 학습한다. VibeThinker는 이미 나와 있던 Qwen2.5-Coder-3B라는 작은 모델을 가져다 다시 가르치기만 했다. 새 모델을 만든 게 아니라, 기존 모델을 다듬은 것이다.

 

둘째, 크기로 승부하지 않았다. 보통은 성능을 올리려면 모델을 키운다. VibeThinker는 반대로 갔다. 작은 모델 그대로 두고, 잘 가르치는 방법으로만 끌어올렸다. "더 큰 두뇌"가 아니라 "더 나은 공부법"으로 승부한 셈이다.

 

본론에 앞서 한 가지. 이 글에서 다루는 정보의 출처는 세 종류이고, 신뢰 수준이 다르다. 모델 구조나 크기는 공개 자료라 확실하지만, 성능 점수는 아직 제작사 주장 단계다. 그 빈틈을 직접 돌려본 결과로 메운다.

 

정보 출처 검증 상태
모델 구조·크기·학습 방식 기술 리포트, 공개 가중치 확실 (누구나 확인 가능)
공식 벤치마크 점수 제작사 자체 보고 미검증 (독립 평가 전)
이 글의 실측 직접 맥북에서 실행 직접 확인

 

참고로 arXiv도 GitHub도 검증 기관이 아니다. 논문을 올리는 게시판이고 파일을 올리는 창고일 뿐이다. "공개됐다"는 누가 보증했다는 뜻이 아니라, 누구나 직접 받아 확인할 수 있다는 뜻이다.

3B는 얼마나 작은가

파라미터는 모델이 학습으로 얻은 "지식과 감각의 양"이다. 사람으로 치면 뇌의 신경 연결 수에 가깝고, 보통 많을수록 똑똑하다.

"30억 개"가 감이 안 오니 다른 모델과 비교해 보자. 단, Anthropic·OpenAI는 모델 파라미터 수를 공개하지 않는다. 아래 큰 모델 수치는 업계 추정치다.

모델 파라미터 (추정) VibeThinker대비
GPT-3 (2020) 1,750억 약 58배
GPT-4 약 1.8조 (추정) 약 600배
Claude Opus 1조~수조 (비공개·추정) 수백~수천 배
VibeThinker-3B 30억 기준

 

체급으로 치면 라이트급과 헤비급이다. 그 격차가 용량으로도 드러난다. VibeThinker는 약 6.7GB라 일반 노트북 한 대에서 돌아간다. 거대 모델이 데이터센터를 요구하는 것과 대조적이다.

특징이 하나 더 있다. 이건 직접 다운로드해 쓰는 공개형(open-weight) 모델이다. Claude나 ChatGPT는 회사 서버에서 빌려 쓰지만, 이건 파일을 내 컴퓨터로 받아 돌린다. 의심되면 직접 받아 검증할 수 있다는 뜻이고, 이 글이 그렇게 했다.

비결: 잘 가르치는 방법

서론에서 말한 "다시 가르치기"가 정확히 뭔지 보자. AI를 만드는 과정은 두 단계인데, 학생에 비유하면 명확하다.

단계 비유 비용 VibeThinker
사전학습 초중고 12년 기초 교육 매우 큼 안 함 (남의 모델을 빌림)
후처리 수능 직전 집중 과외 상대적으로 작음 직접 함

 

헷갈리기 쉬운 점 하나. 사전학습이냐 후처리냐는 양자택일이 아니다. 거의 모든 모델이 둘 다 거친다. Opus, Fable 같은 큰 모델도 전 과정을 직접 한다. VibeThinker의 차이는 사전학습을 안 한 게 아니라, 비싼 기초 교육을 직접 하지 않고 남의 모델을 빌려 쓴 뒤 과외만 했다는 점이다.

이 과외법의 이름이 Spectrum-to-Signal이다. 먼저 다양한 풀이를 넓게 가르치고(스펙트럼), 그중 맞는 풀이만 골라 강화한다(신호). 디테일 하나가 인상적이다. 너무 쉬운 문제는 일부러 뺐다. 사람도 아는 걸 반복하면 안 늘듯이.

비용도 작다. Raschka의 추정으로 대략 2만5천~6만 달러다. 거대 모델 학습의 수백만~수천만 달러에 비하면 미미하다.

공식 점수

이 모델은 만능이 아니다. 정답이 딱 떨어지는 문제, 즉 수학과 코딩에 특화됐다.

시험 점수 종류
AIME 2026 94.3 수학경시
LiveCodeBench v6 80.2 코딩
IMO-AnswerBench 76.4 올림피아드 수준
GPQA-Diamond 70.2 폭넓은 지식

 

가장 믿을 만한 근거는 시험 후에 새로 나온 문제로 테스트한 것이다. 2026년 4~5월 최신 LeetCode 대회 문제 128개 중 123개를 첫 시도에 통과했다. 96.1%다. 모델이 만들어진 뒤에 나온 문제라, 외워서 풀 수 없다. 진짜 일반화의 신호다.

단, 폭넓은 지식(GPQA)에서는 70점으로 큰 모델과 격차가 남는다. 수학·코딩은 정상급, 일반 지식은 평범. 이 패턴을 기억해두면 다음 장이 더 잘 읽힌다.

 

직접 돌려본 실측 

맥북 에어(M칩, 16GB)에 받아 직접 돌렸다. 도구는 mlx-lm, 8bit 버전, 제작사 권장 설정(temperature 1.0, top_p 0.95)을 그대로 썼다. 강점이라는 수학·코딩이 진짜인지 확인하고, 약점일 한국어를 일부러 공략한다. 결과를 먼저 한 표로 요약하면 이렇다.

테스트 무엇을 물었나 결과 평가
1. 수학 1~100의 3 또는 5의 배수 합 정답(2418). 틀렸다가 스스로 교정 + 교차검증 후 정답 통과
2. 코딩 신규 알고리즘 문제 (Claude와 비교) 가장 빠른 풀이 도달 + 증명까지 자발 작성 통과 (Claude급)
3. 한국어 한국 속담 뜻 + 비슷한 속담 오역 + 가짜 속담 지어냄(환각) 실패

 

테스트 1. 수학

던진 문제 1부터 100까지 정수 중 3 또는 5의 배수의 합을 구하라. (정답: 2418)

 

맞혔다. 그런데 단순히 맞힌 게 아니다. 풀이 도중 첫 항을 잘못 잡아 틀린 값을 냈다가, 스스로 오류를 발견하고 정정하는 과정이 그대로 드러났다.

모델의 추론 일부 (원문) "earlier we computed 1650. Let's check: ... first term is 3 not 1. ... Sum_3 = 1683, not 1650." → 처음에 1650으로 계산 → "첫 항이 1이 아니라 3"이라고 자기 교정 → 1683으로 정정

 

거기서 멈추지 않았다. 공식으로 2418을 구한 뒤, 47개 숫자를 직접 나열해 그룹별로 더하는 완전히 다른 방법으로 한 번 더 검증했다.

"Let's quickly list and sum manually to verify. ... (47개 수를 6~7개씩 묶어 합산) ... Total = 2418. Yes matches."

 

시키지 않았는데도 스스로 두 가지 방법으로 교차검증한 것이다. 16GB 맥북에서 초당 약 32토큰, 메모리 3.5GB로 돌았다.

테스트 2. 코딩 — Claude와 비교

인터넷에 풀이가 없는 신규 문제를 직접 만들었다. 외운 답을 못 쓰게 하려는 것이다.

던진 문제 (요약) 정수 배열 nums와 정수 k가 있다. 부분배열의 (최댓값 − 최솟값)이 k 이하이면 "balanced"다. 가장 긴 balanced 부분배열의 길이를 반환하라. 제약: 길이 최대 10⁵.

 

제약이 배열 길이 최대 10만이라, 초보적으로 풀면 너무 느려서 시간 초과로 실패한다. 효율적인 풀이를 찾아야 통과한다. 같은 문제를 VibeThinker와 Claude에게 동시에 시켰다.

VibeThinker가 내놓은 핵심 코드다.

 

from collections import deque
def longestBalanced(nums, k):
    max_d = deque()   # 감소덱 → 현재 최댓값
    min_d = deque()   # 증가덱 → 현재 최솟값
    left = 0; best = 0
    for right, val in enumerate(nums):
        while max_d and nums[max_d[-1]] <= val: max_d.pop()
        max_d.append(right)
        while min_d and nums[min_d[-1]] >= val: min_d.pop()
        min_d.append(right)
        while nums[max_d[0]] - nums[min_d[0]] > k:   # 윈도우 축소
            if max_d[0] == left: max_d.popleft()
            if min_d[0] == left: min_d.popleft()
            left += 1
        best = max(best, right - left + 1)
    return best
항목 VibeThinker-3b Claude
정답 맞음 맞음
속도(효율) 가장 빠른 풀이 도달 동일
풀이 방식 슬라이딩 윈도우 + 단조 덱 2개 동일
추가 정답임을 증명까지 자발적으로 작성 코드+설명

 

여기서 "속도"가 핵심이다. 같은 문제도 초보적으로 풀면 데이터가 커질 때 급격히 느려져(연산 약 100억 번) 실무에선 못 쓴다. 가장 효율적인 풀이는 데이터에 정비례해서(약 10만 번) 빠르다. VibeThinker는 정답만 맞힌 게 아니라 가장 빠른 풀이까지 스스로 찾아냈다. 게다가 Claude와 거의 동일한 접근을 독립적으로 도출했고, 시키지도 않은 "이 풀이가 맞다는 증명"까지 붙였다. 검증 가능한 추론에 특화됐다는 주장이 코드에서도 드러났다.

테스트 3. 한국어 — 약점 공략

이번엔 일부러 약점을 노렸다. 정답이 검증 불가능하고, 한국어이며, 한국 고유 지식인 속담을 골랐다.

던진 문제 '서당 개 삼 년이면 풍월을 읊는다'의 뜻을 설명하고, 비슷한 의미의 속담을 두 개 들어라. (정답: 무지한 사람도 유식한 환경에 오래 있으면 자연히 견문이 생긴다)

 

속담을 통째로 이해하지 못하고, 글자 하나하나를 영어로 분해하려다 길을 잃었다.

모델의 추론 (원문 발췌) "서당개 삼 Gothic? ... '서당개' might be a place name? ... maybe 'south school'? ... '풍월' = harvest moon? ... I'm overthinking. ... Not sure."

 

추론 과정에 영어·중국어·아랍어·깨진 토큰이 마구 뒤섞이며 "Not sure", "I'm overthinking"을 수십 번 반복했다. 그러고는 끝내 존재하지도 않는 가짜 속담 두 개를 지어냈다.

모델의 최종 답 (환각) 속담 뜻을 "남쪽 학교의 삼중 교리를 따르면 추수달을 즐긴다"로 오역. 비슷한 속담이라며 "서대·3-path", "서대·시-경" 같은 실재하지 않는 표현을 만들어, 로마자 표기와 영어 번역까지 붙여 표로 제시.

 

틀린 줄도 몰랐다. 답 하나에 7,166 토큰을 썼다. 수학(3,483)과 코딩(4,505)의 두 배다. 정답이 없는 영역에서 헤맬수록 토큰만 더 쏟은 것이다.

같은 모델이다. 수학과 코딩에선 Claude급이었는데, 한국 속담 하나에 가짜 답을 지어냈다.

수학과 코딩은 통과했고, 한국어는 무너졌다. 같은 모델에서 결과가 정확히 갈린 것이다.

무엇을 가져갈까

첫 번째 교훈이 왜 우리 일과 연결되는지 짚고 넘어가자. 비약처럼 보일 수 있어서다.

VibeThinker가 증명한 건 이것이다. 모델의 능력은 크기만으로 정해지지 않는다. 같은 재료(작은 모델)라도 어떻게 다루느냐에 따라 결과가 크게 달라진다. 거기서 "다루는 방법"이 후처리, 즉 좋은 데이터로 잘 가르치는 일이었다.

우리는 모델을 후처리할 일이 없다. 그건 만든 쪽의 영역이다. 하지만 모델을 "다루는" 또 다른 지점이 우리에게 있다. 모델에게 매번 건네는 컨텍스트 — CLAUDE.md, 스킬 문서, 프롬프트다. 모델 자체는 고정돼 있어도, 그 모델에게 무엇을 어떻게 알려주느냐는 우리가 매일 바꿀 수 있다.

원리가 같다. VibeThinker는 "잘 큐레이션한 데이터"로 모델을 끌어올렸고, 우리는 "잘 정리한 지침"으로 같은 모델에게서 더 나은 답을 끌어낸다. 둘 다 모델을 키우지 않고, 모델에 주는 입력의 질을 높여 성능을 얻는다. 실제로 같은 질문이라도 두서없이 던질 때와 맥락·제약·예시를 정리해 줄 때 답의 품질이 확연히 갈리는 걸 누구나 경험한다.

정리하면, "큰 모델 쓰면 되겠지"가 아니라 "지금 쓰는 모델에 줄 지침부터 다듬자"가 먼저다.

비용 없이 당장 할 수 있는 개선이고, 효과도 크다.
