# 기획: Orca 사용법 - 여러 CLI 에이전트를 워크트리로 병렬 실행하는 방법

## 분류와 독자

- 상위 카테고리: `Log`
- 하위 카테고리: `AI 개념 · 실전`
- 한 명의 독자: Codex나 Claude Code 같은 CLI 코딩 에이전트를 하나씩
  사용해 봤고, 한 저장소에서 여러 작업을 안전하게 병렬화하고 싶은 개발자
- 검색 의도: Orca가 무엇인지, 단순 터미널 분할과 무엇이 다른지 이해한 뒤
  설치부터 첫 병렬 세션, 검토와 정리까지 재현하고 싶음
- 독자가 이미 아는 것: Git 저장소, 브랜치, 터미널, CLI 코딩 에이전트의
  기본 개념

## 글의 중심

- 독자가 기억할 한 문장: Orca의 핵심 가치는 에이전트 수가 아니라 작업마다
  독립된 Git worktree와 브랜치를 주고, 결과를 diff로 비교해 선택하게 만드는
  검토 흐름입니다.
- 낯선 주제를 붙잡아 줄 익숙한 장면: 한 저장소에서 두 터미널을 열어 같은
  브랜치를 건드리다가 한쪽 변경이 다른 쪽 테스트를 깨뜨리는 상황
- 이 글이 답하지 않는 범위: Orca 앱의 모든 자동화·원격 서버·모바일 기능,
  개별 AI 모델의 품질 비교, 팀 단위 보안 심사
- 가장 정직한 한계 또는 반론:
  - worktree는 작업 디렉터리를 격리하지만 운영체제 권한, 외부 데이터베이스,
    포트, 클라우드 자격 증명까지 격리하는 보안 샌드박스가 아님
  - 서로 같은 줄을 고친 브랜치는 최종 병합 단계에서 여전히 충돌함
  - 병렬 수를 늘리면 구독 사용량, CPU·메모리, 사람이 검토할 diff도 함께
    늘어남
  - Orca 앱 자체를 설치해 UI를 실행한 사용 후기가 아니라, 공식 문서 검토와
    핵심 Git worktree 메커니즘의 Codex 재현 실험임

## dev.log만의 근거

- first-party contribution:
  - 작은 Git 저장소에서 기준 checkout과 `agent-a`, `agent-b` worktree를 생성
  - 두 worktree의 같은 파일에 서로 다른 값을 써도 기준 checkout은 깨끗하게
    유지되는지 확인
  - 두 변경을 각각 커밋한 뒤 차례로 병합해 두 번째 병합의 충돌을 재현
  - 이 결과를 기반으로 Orca 도입 기준과 안전한 첫 세션 체크리스트 구성
- 실제 실행 주체: `Codex`
- 보존할 원자료:
  - `artifacts/run-worktree-isolation.sh`
  - `artifacts/worktree-isolation-output.txt`
  - `artifacts/source-snapshot.md`
- 기존 글 또는 시리즈 연결: dev.log의 AI 모델 비교 글이 “무슨 모델을
  쓸지”를 다뤘다면, 이번 글은 여러 CLI 에이전트의 작업공간을 어떻게
  운영하고 검토할지 다룸
- 다른 블로그 이름으로 바꿔도 성립하는 부분: 설치 절차와 공식 기능 요약
- dev.log에 남는 고유한 부분: 격리 성공과 병합 충돌을 함께 재현한 원자료,
  병렬 수보다 검토 가능성을 우선하는 도입 판단표

## 설명 순서

| 순서 | 독자가 먼저 알아야 할 것 | 다음 내용과의 연결 |
|---|---|---|
| 1 | Orca는 AI 모델이 아니라 여러 CLI 에이전트를 관리하는 데스크톱 ADE | 어떤 구성요소를 묶는지 이해 |
| 2 | Git worktree는 같은 저장소의 여러 브랜치를 별도 폴더로 checkout하는 기능 | 병렬 작업 중 파일 덮어쓰기를 피하는 원리 |
| 3 | worktree별 터미널·브랜치·브라우저와 diff 검토 흐름 | Orca의 장점과 첫 세션 사용법 |
| 4 | worktree는 보안 샌드박스가 아니며 병합 충돌도 제거하지 않음 | 권한·비용·병렬 수 운영 원칙 |
| 5 | 설치 -> 저장소 추가 -> worktree 생성 -> 에이전트 실행 -> diff 비교 -> commit/push | 독자가 직접 재현할 시작 절차 |

## 중앙 방법의 판단 사슬

`하나의 Git 저장소와 기준 ref -> 작업별 독립 worktree·브랜치 -> 각 worktree에서 CLI 에이전트 실행 -> 테스트와 diff 비교 -> 채택할 변경만 commit·push·PR -> 나머지 worktree 정리`

## 보조 인포그래픽 판단

- 결정: 본문 이해를 돕는 과정형 인포그래픽 1장을 추가합니다.
- 독자 질문: 하나의 저장소가 Orca에서 어떻게 두 작업으로 나뉘고, 무엇을
  거쳐 하나의 변경으로 채택되나요?
- 시각화할 관계: `기준 저장소 -> Worktree A·B로 분리 -> 같은 성공 조건과
  테스트로 실행 -> diff 검토로 다시 모임 -> 채택안만 commit·push·PR,
  나머지는 정리`
- 글만으로 부족한 이유: 분기와 합류가 여러 절에 걸쳐 설명되고, worktree가
  맡는 작업공간 격리와 사람이 맡는 diff 검토의 경계가 문장만으로는 한눈에
  잡히지 않습니다.
- 유형: 과정
- 권장 삽입 위치: `1. Orca의 정확한 역할` 마지막 설명 뒤, `2. 여러 CLI
  에이전트를 함께 쓰기 쉬워지는 이유` 앞
- 추가 이미지: 같은 관계를 반복하는 두 번째 보조 이미지는 만들지 않습니다.
- 제작 원칙: 한글 문구와 화살표는 HTML/SVG로 결정론적으로 배치하고, 최종
  PNG와 편집 가능한 원본을 함께 보존합니다.

## 독자가 이어서 물을 질문

- VS Code 터미널 여러 개를 여는 것과 무엇이 다른가요?
- worktree를 쓰면 병합 충돌도 사라지나요?
- Codex와 Claude Code를 먼저 따로 설치해야 하나요?
- 에이전트 세 개를 꼭 띄워야 하나요?
- 기본 권한 우회 옵션을 그대로 사용해도 안전한가요?
- 같은 서버 포트와 데이터베이스를 여러 worktree가 함께 써도 되나요?
- 어떤 작업을 병렬화하고 어떤 작업은 순서대로 해야 하나요?
- 결과가 서로 다를 때 무엇을 기준으로 고르나요?

## 추천의 범위

- 순위 유형: 전체 성능 순위나 벤치마크가 아니라 실용 도입 추천
- 기본 선택: 처음에는 에이전트 두 개, 서로 다른 worktree, 같은 성공 조건,
  수동 권한 모드로 시작
- 예외: 한 번만 실행할 짧은 순차 작업, Git을 쓰지 않는 프로젝트, diff를
  검토할 사람이 없는 상황에서는 기존 CLI 하나가 더 단순함
