안녕하세요. dev.log입니다.

화상회의에서 Claude Code 화면을 공유하면 상대방은 작업 과정을 볼 수 있습니다.
하지만 프롬프트를 입력하는 키보드는 여전히 한 사람에게만 있습니다. `ccshare`는
이 불편을 같은 터미널에 여러 사람이 들어와 함께 입력하는 방식으로 바꾼
도구입니다. **편리한 만큼 초대 코드는 화면 링크가 아니라 내 컴퓨터의 셸에 접근하는 열쇠로 다뤄야 합니다.** 처음에는 읽기 전용·로컬 전용으로 열고,
신뢰하는 사람에게만 입력권을 주는 편이 안전합니다.

현재 `ccshare`의 이름은 `manycode`로 바뀌었습니다. 이름이 왜 달라졌는지부터
실제 작동 구조, 직접 재현한 19개 테스트, 상황별 안전한 시작 명령까지
차례로 살펴보겠습니다.

### ccshare와 manycode의 관계

공식 [README](https://github.com/unworld11/manycode)는 이 도구가 2026년 7월까지
`ccshare`라는 이름을 썼고, 더 넓은 용도를 담기 위해 `manycode`로 바꿨다고
설명합니다. Claude Code만이 아니라 Codex, OpenCode, Kimi처럼 터미널에서
상호작용하는 다른 코딩 에이전트도 공유할 수 있기 때문입니다.

기존 사용자가 바로 명령을 바꿔야 하는 것은 아닙니다. 확인한 v0.6.0의
`package.json`에서는 `manycode`와 `ccshare`가 같은 실행 파일을 가리킵니다.
예전 명령은 별칭으로 남지만, 이 글에서는 현재 이름인 `manycode`를 사용합니다.

### 화면 공유와 다른 구조

manycode는 완성된 대화 기록을 링크로 공개하는 서비스가 아닙니다. 호스트의
프로젝트 폴더에서 실제 에이전트를 실행하고, 그 **살아 있는 터미널 한 개를 여러 사람이 같이 쓰는 도구**입니다.

여기서 PTY는 프로그램이 자신을 일반 파일이 아니라 터미널 안에서 실행 중이라고
느끼게 만드는 가상 터미널입니다. manycode가 Claude Code나 Codex를 PTY 안에서
실행하면, 참가자는 같은 화면을 받아 보고 자신의 키 입력을 그 PTY로 돌려보냅니다.

`프로젝트 폴더 -> manycode의 PTY -> Claude Code·Codex 실행 -> 화면 전송 -> 참가자 입력이 같은 PTY로 복귀`

화면 공유와의 차이를 간단히 나누면 다음과 같습니다.

| 방식 | 상대방의 입력 | 공유되는 작업 상태 |
|---|---|---|
| 일반 화면 공유 | 기본적으로 불가 | 화면만 관찰 |
| manycode 기본값 | 가능 | 같은 터미널과 에이전트 세션 |
| manycode 읽기 전용 | 차단 | 같은 화면만 관찰 |

호스트가 `manycode host codex`처럼 실행할 프로그램을 지정할 수도 있습니다.
명령을 생략하면 기본 에이전트인 Claude Code를 실행합니다. 참가자는 같은
Wi-Fi에서 CLI로 찾거나, 직접 주소·터널·브라우저 링크로 접속합니다.

### 직접 재현한 19개 테스트

기능 소개만 옮기지 않기 위해 2026년 7월 28일 공식 저장소의 커밋
`3c43052`를 내려받아 테스트했습니다. 환경은 Apple Silicon의 macOS 26.5.2,
Node.js 26.0.0, npm 11.12.1입니다. 공식 수동 설치 방법대로 의존성을 설치한
뒤 저장소가 제공하는 `npm test`를 실행했습니다.

판정 기준은 단순합니다. 각 시나리오가 `PASS`를 출력하고 전체 프로세스가
오류 없이 끝나야 통과입니다. 실제 Claude Code 대신 테스트용 bash 프로세스를
PTY에서 실행하므로, 아래 결과는 **터미널 공유 계층의 동작을 확인한 결과**이지
Claude 모델의 성능 평가가 아닙니다.

최종 실행에서는 19개 항목이 모두 통과했습니다.

| 확인 영역 | 통과 수 | 실제로 확인한 범위 |
|---|---:|---|
| 연결과 전송 | 3/3 | 직접 연결, 릴레이, 느린 참가자 정리 |
| 입력·종료 경계 | 7/7 | 코드 정규화, 잘못된 옵션·없는 명령 거부, 버전·원격 종료 |
| 브라우저·승인 | 3/3 | 브라우저 페이지, 참가 승인과 거절 |
| 세션 채팅 | 3/3 | 발신자 표시, 자기 메시지 미반향, 늦은 참가자의 로그 |
| 비밀값·녹화 | 3/3 | `.env` 마스킹, 원문 공유 옵션, asciinema 파일 |

처음 두 번은 `stop <code>` 항목 하나만 같은 방식으로 실패했습니다. 원인을
따라가 보니 제품의 종료 로직보다 샌드박스가 `~/.manycode/sessions` 상태 파일
쓰기를 막은 영향이었습니다. 그 경로만 허용하고 같은 테스트를 다시 실행하자
19개가 모두 통과했습니다. 이 과정은 환경 권한이 막힌 실패와 제품 결함을
구분해야 한다는 점도 보여 줬습니다.

다만 실제 지인을 외부 네트워크로 초대해 장시간 사용하지는 않았습니다.
Cloudflare 터널의 체감 지연, 다섯 명이 동시에 입력할 때의 충돌, 운영 저장소의
보안 적합성은 이번 결과만으로 판단할 수 없습니다.

### 설치와 첫 로컬 공유

공식 사이트는 설치 스크립트 한 줄을 안내합니다.

```bash
curl -fsSL https://manycode.vercel.app/install.sh | sh
```

원격 스크립트를 바로 셸에 넘기는 방식이 부담스럽다면, 먼저
[공식 저장소](https://github.com/unworld11/manycode)를 확인하고 수동으로
설치할 수 있습니다. 이번 검증도 아래 경로를 사용했습니다.

```bash
git clone https://github.com/unworld11/manycode.git
cd manycode
npm install
npm link
manycode setup
```

`manycode setup`은 표시 이름과 기본 에이전트, 터널·메뉴 막대·참가 승인 설정을
저장합니다. 공식 요구 사항은 Node.js 18 이상입니다. Mac에서는 DMG 앱도
제공하지만 v0.6.0 안내상 서명되지 않은 빌드이므로, 출처와 릴리스를 확인한 뒤
실행하는 편이 좋습니다.

첫 테스트는 실제 프로젝트가 아닌 임시 폴더에서 읽기 전용·로컬 전용으로 여는
방법을 권합니다.

```bash
mkdir manycode-demo
cd manycode-demo
manycode host --read-only --no-tunnel
```

호스트 화면에 여섯 자리 코드가 나오면 같은 Wi-Fi의 참가자가 다음처럼
접속합니다.

```bash
manycode join 7KQ2FM
```

이 단계에서는 상대가 같은 화면은 보지만 키 입력은 반영되지 않습니다. 읽기
전용 동작과 참가자 이름이 제대로 보이는지 확인한 뒤, 정말 함께 입력해야 할
때만 쓰기 권한을 여는 순서가 좋습니다.

### 신뢰하는 사람과 함께 입력하기

같은 네트워크에서 신뢰하는 사람과 페어 프로그래밍할 때는 macOS의 참가 승인
옵션을 더할 수 있습니다.

```bash
manycode host --approve --no-tunnel
```

`--approve`를 켜면 올바른 코드를 가진 참가자도 호스트가 허용할 때까지
대기합니다. 공식 테스트에서도 승인된 참가자는 `hold -> ok`, 거절된 참가자는
`hold -> err` 순서로 처리됐습니다.

여기에는 플랫폼 제한이 있습니다. 현재 참가 승인 창은 macOS의 대화상자를
사용합니다. 다른 운영체제에서는 공식 소스상 참가자를 자동으로 받아들이므로,
`--approve`만 믿어서는 안 됩니다. 먼저 `--read-only`를 쓰거나, 코드를
신뢰하는 사람에게만 전달해야 합니다.

다른 네트워크의 참가자가 꼭 필요하면 기본 Cloudflare Quick Tunnel을 사용할
수 있습니다. 별도 계정 없이 임시 `trycloudflare.com` 주소가 생기고, 참가자는
CLI나 브라우저로 접속합니다. 반대로 같은 Wi-Fi만 쓸 때는 `--no-tunnel`을
명시해 세션을 인터넷에 열지 않는 편이 더 단순합니다.

### 공유 코드가 지키지 못하는 것

공식 문서는 **공유 코드가 유일한 인증 수단**이라고 분명히 밝힙니다. 코드를
가진 참가자는 기본 설정에서 호스트 컴퓨터의 실제 셸에 명령을 입력할 수
있습니다. 링크를 공개 채널에 올리거나 모르는 사람을 받아서는 안 되는 이유입니다.

상황별 기본값은 다음처럼 잡을 수 있습니다.

| 상황 | 권장 시작 옵션 | 이유 |
|---|---|---|
| 기능 시연 | `--read-only --no-tunnel` | 입력과 인터넷 공개를 함께 차단 |
| 같은 Wi-Fi의 페어 작업 | `--approve --no-tunnel` | macOS에서 참가자를 확인한 뒤 입력 허용 |
| 원격 페어 작업 | `--approve` | 터널은 열되 참가자를 한 번 더 확인 |
| 불특정 다수 공개 | 사용하지 않음 | 짧은 코드로 실제 셸을 공유하기 때문 |

뒤늦게 참가한 사람은 최근 256KB의 터미널 출력을 다시 받습니다. 초대 전에
화면에 출력한 내용도 일부 보일 수 있다는 뜻입니다. `.env` 파일의 값은
기본값에서 `••••••`로 가려지며, 이번 테스트에서도 마스킹과 원문 공유 옵션이
각각 예상대로 작동했습니다.

그래도 이를 비밀 관리 도구로 보면 곤란합니다. 공식 보안 설명처럼 마스킹은
`.env`에 적힌 값과 정확히 일치하는 바이트를 찾는 방식입니다. 인코딩하거나
일부만 잘라 출력한 값, 다른 파일에 든 비밀, 명령 기록까지 모두 찾아내지는
못합니다. 공유 전에는 실제 자격 증명을 빼고 별도 테스트 계정을 쓰는 편이
안전합니다.

자체 릴레이를 운영한다면 `wss://`처럼 TLS를 적용해야 합니다. 공식 문서는
릴레이가 터미널 바이트를 볼 수 있고, 릴레이 경로의 참가 승인은 참가자별 입력을
완전히 구분하지 못해 best-effort라고 설명합니다.

### 잘 맞는 용도와 맞지 않는 용도

manycode가 가장 잘 맞는 장면은 화면 공유보다 한 단계 더 적극적인 협업입니다.

- 페어 프로그래밍 중 번갈아 프롬프트를 입력할 때
- 통화 중 같은 오류를 보며 디버깅할 때
- 처음 쓰는 사람에게 코딩 에이전트 조작을 보여 줄 때
- 비개발자가 시작한 세션을 신뢰하는 개발자에게 잠시 넘길 때

반면 여러 에이전트가 각자 독립된 작업을 병렬로 처리하는 도구는 아닙니다.
모두 같은 PTY와 같은 작업 상태를 봅니다. 제작자도 Product Hunt 답변에서 동시
입력 잠금이나 턴제가 없고 공유 키보드에 가깝다고 설명했습니다. 별도 채팅은
누가 입력할지 조율하는 데 도움이 되지만, 여러 사람이 동시에 타이핑하면 입력이
섞일 수 있다는 전제로 써야 합니다.

결론적으로 ccshare, 현재 이름 manycode의 장점과 위험은 같은 구조에서 나옵니다.
상대가 구경만 하는 화면 공유를 넘어 함께 문제를 풀 수 있지만, 그만큼 실제
셸의 제어권도 나눕니다. **첫 실행은 `--read-only --no-tunnel`, 다음 단계는 신뢰하는 사람과 `--approve --no-tunnel`**로 시작해 보세요. 원격 터널은 그 두
단계를 확인한 뒤 꼭 필요할 때 여는 순서가 가장 이해하기 쉽습니다.
