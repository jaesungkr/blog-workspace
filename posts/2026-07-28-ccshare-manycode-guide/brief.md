- 하위 카테고리: `개발 · 디지털`

  세션에 직접 입력할 수 있는 방법을 찾는 개발자
- 검색 의도: `ccshare`, `ccshare 사용법`, `Claude Code 공유`, `manycode`를

## 글의 중심

- 독자가 기억할 한 문장: ccshare, 현재 이름 manycode는 화면을 보내는 도구가
  아니라 하나의 실제 터미널 입력권을 나누는 도구이므로, 첫 공유는
  `--read-only --no-tunnel`로 시작하고 신뢰하는 사람에게만 쓰기 권한을 열어야 함
- 낯선 주제를 붙잡아 줄 익숙한 장면: 화상회의 화면 공유에서는 상대가 볼 수만
  있고, 프롬프트를 대신 입력하려면 내용을 읽어 주거나 복사해 보내야 하는 장면
- 이 글이 답하지 않는 범위: 실제 외부 네트워크의 장시간 지연, 다섯 명이 동시에
  타이핑할 때의 UX, Windows·Linux의 네이티브 앱 동작, 기업 보안 적합성
- 가장 정직한 한계 또는 반론: 공식 테스트를 로컬에서 재현했지만 실제 지인과
  Cloudflare 터널로 프로덕션 저장소를 공유하지 않았음. 소스는 공개됐어도 짧은
  코드가 유일한 인증이라는 구조적 위험은 남음

## 중앙 방법의 계산 또는 판단 사슬

`호스트의 프로젝트 폴더 -> manycode가 PTY에서 Claude Code·Codex 실행 ->
터미널 출력 프레임을 참가자에게 전송 -> 참가자의 키 입력을 같은 PTY로 반환 ->
모두 같은 화면과 작업 상태 확인`

안전 판단 사슬:

`참가자가 보기만 하는가 -> 같은 네트워크인가 -> 참가자를 신뢰하는가 ->
macOS 승인 창을 쓸 수 있는가 -> 외부 터널이나 릴레이가 꼭 필요한가 ->
읽기 전용·LAN 전용·승인형·원격형 중 선택`

## 보조 인포그래픽 판단

- 결정: `1장`
- 한눈에 보여 줄 관계: 호스트의 에이전트가 PTY 하나에서 실행되고, 출력은
  호스트·CLI 참가자·브라우저 참가자에게 나가며 입력은 같은 PTY로 돌아오는
  양방향 구조. 공유 코드와 `--approve`, `--read-only`, `--no-tunnel`의 보안
  경계를 함께 표시함
- 글이나 표만으로 충분하지 않은 이유: 설치 명령보다 중요한 것은 출력 공유와
  셸 입력권이 같은 연결에서 반대 방향으로 흐른다는 점입니다. 이 관계는 세
  참가 경로와 네 개의 보호 옵션을 한 화면에 놓을 때 더 빨리 이해됨
- 유형: `원리`
- 핵심 설명 뒤 권장 위치: `화면 공유와 다른 구조` 절의 PTY 설명과 흐름 목록 바로 뒤
- 추가 이미지가 있다면 각 이미지가 답할 서로 다른 질문: 1장으로 충분함

## 독자가 이어서 물을 질문

- ccshare와 manycode는 다른 도구인가요? -> 같은 도구이며 2026년 7월 이름이
  바뀌었고 `ccshare` 명령도 별칭으로 남았다고 설명함
- 상대방은 화면만 보나요? -> 기본값은 입력 가능이며 `--read-only`일 때만 보기
  전용이라고 설명함
- 초대 코드를 모르는 사람은 들어올 수 없나요? -> 공식 문서상 코드가 유일한
  인증이므로 코드를 노트북 열쇠처럼 다뤄야 한다고 설명함
- `.env` 마스킹이면 안전한가요? -> 파일의 값과 정확히 일치하는 바이트를 가릴
  뿐, 인코딩되거나 변형된 값은 샐 수 있어 보조 장치라고 설명함
- 결국 무엇부터 쓰나요? -> 첫 시연은 `--read-only --no-tunnel`, 신뢰하는
  macOS 페어 작업은 `--approve --no-tunnel`, 원격 터널은 필요할 때만 권함
