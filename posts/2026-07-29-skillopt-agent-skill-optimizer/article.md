안녕하세요. dev.log입니다.

Codex나 Claude Code에 같은 종류의 일을 반복해서 맡기다 보면 비슷한 실수도
반복됩니다. 코드를 고친 뒤 테스트를 빼먹거나, 정해 둔 출력 형식을 자꾸 놓치는
식입니다. 그때마다 `SKILL.md`에 규칙을 보탤 수 있지만, 새 규칙이 다른 작업까지
망가뜨리지 않았는지 확인하기는 어렵습니다.

`SkillOpt`는 바로 이럴 때 쓰는 도구입니다. 모델 자체를 다시 학습하는 대신
**에이전트의 작업 설명서인 `SKILL.md`를 조금씩 고치고, 다른 문제에서도 성적이 오른 수정만 남깁니다.**
한 번 묻고 끝나는 대화나 정답을 매기기 어려운 창작에는 굳이 필요하지 않습니다.

### SkillOpt가 필요한 순간: 테스트를 자꾸 빼먹는 에이전트

팀에서 버그 수정용 스킬을 반복해서 쓴다고 가정해 보겠습니다. 현재 스킬에는
"문제를 분석하고 코드를 수정한다"는 절차만 있고, 에이전트는 코드를 고친 뒤
관련 테스트를 실행하지 않는 실수를 여러 번 보였습니다.

SkillOpt는 실패한 작업 기록을 읽고 다음과 같은 규칙을 후보로 제안할 수 있습니다.

`코드를 수정한 뒤 관련 테스트를 실행하고, 실패가 남으면 원인을 고친 후 마무리한다.`

규칙이 그럴듯하다는 이유만으로 바로 채택하지는 않습니다. 규칙을 만드는 데 쓰지
않은 별도 문제 묶음으로 현재 스킬과 후보 스킬을 다시 비교합니다. 이 별도 문제
묶음을 **선택용 작업(selection set)**이라고 부릅니다.

아래 숫자는 실제 벤치마크 결과가 아니라 작동 방식을 보여 주기 위한 가상 예시입니다.

| 비교 대상 | 선택용 작업 10개 결과 | 판단 |
|---|---:|---|
| 현재 스킬 | 6개 성공 | 비교 기준 |
| 테스트 확인 규칙을 넣은 후보 | 8개 성공 | 점수가 올라 채택 |
| 표현만 바뀌고 결과가 같은 후보 | 6개 성공 | 동점이라 거절 |

여기까지가 SkillOpt가 하는 일의 핵심입니다. **반복된 실패에서 작은 규칙을 제안하고, 처음 보지 않은 문제에서도 나아졌을 때만 작업 설명서에 남깁니다.**

이 가상 예시는 구조를 설명하기 위한 것입니다. 실제 코드도 같은 원칙으로
움직이는지 확인하려고 Codex가 현재 소스의 전체 테스트와 검증 게이트를
직접 실행했습니다.

### 모델이 아니라 작업 설명서를 고치는 도구

SkillOpt에서 스킬은 에이전트에게 작업 절차를 알려 주는 자연어 문서입니다.
도구를 어떤 순서로 쓸지, 무엇을 확인할지, 결과를 어떤 형식으로 내놓을지 같은
규칙을 Markdown으로 적습니다. 앞의 예시에서는 "코드 수정 뒤 테스트를
실행한다"는 문장이 여기에 들어갑니다. 학습 중에도 실제 작업을 수행하는
**대상 모델의 가중치는 고정**되고, 바뀌는 것은 이 문서뿐입니다.

스킬 문장을 고치는 별도의 **옵티마이저 모델**도 필요합니다. 쉽게 말해 실제
업무는 대상 모델이 하고, 작업 기록을 읽어 설명서를 편집하는 일은 옵티마이저
모델이 맡습니다. 공식 [논문](https://arxiv.org/abs/2605.23904)은 이를 모델
밖에 놓인 자연어 상태를 훈련하는 방식으로 설명합니다.

무엇을 바꾸고 어떤 증거로 수정안을 남기는지 비교하면 차이가 선명해집니다.

| 방식 | 바꾸는 대상 | 채택 기준과 배포 결과 |
|---|---|---|
| 수동 스킬 작성 | 스킬 문서 전체 | 작성자가 검토한 Markdown 문서 |
| 모델 파인튜닝 | 모델 가중치 또는 어댑터 | 학습·검증 지표를 통과한 모델 또는 어댑터 |
| SkillOpt | 스킬 문서의 제한된 부분 | 분리한 검증 점수가 오르면 `best_skill.md` |

SkillOpt가 파인튜닝과 닮은 훈련 용어를 쓰더라도 두 방법은 같지 않습니다.
가중치를 바꾸지 않으므로 시작 장벽과 배포 형태가 다릅니다. 그렇다고 모델이
원래 갖지 못한 지식을 스킬 파일만으로 모두 넣을 수 있는 것은 아닙니다.

### 예시를 실제 학습으로 바꾸는 여섯 단계

앞의 가상 예시에서는 실패 기록으로 테스트 확인 규칙을 만들고, 별도 문제
10개에서 후보의 점수가 올랐는지 확인했습니다. 실제 SkillOpt도 같은 일을
여러 작업에 걸쳐 자동으로 반복합니다.

작업 데이터는 훈련용, 선택용, 최종 시험용으로 나눕니다. 훈련용 작업은 편집
근거를 만들고, 선택용 작업은 후보를 받아들일지 판단합니다. 최종 시험용 작업은
고른 스킬의 성능을 마지막에 보고할 때만 씁니다. 같은 문제를 보고 수정한 뒤
그 문제로 다시 채점하면 답을 외우는 쪽으로 흐를 수 있어 역할을 나눕니다.

한 번의 수정은 다음 순서로 진행됩니다.

1. 대상 모델이 현재 스킬을 읽고 훈련 작업 묶음을 수행합니다.
2. 실행 메시지, 도구 호출, 결과, 채점 피드백을 하나의 작업 기록으로 모읍니다.
3. 옵티마이저 모델이 성공과 실패를 따로 살펴 `추가·삭제·교체` 편집을 제안합니다.
4. 비슷하거나 충돌하는 편집을 합치고, 중요도 순으로 정렬합니다.
5. 현재 텍스트 학습률이 허용한 개수만 적용해 후보 스킬을 만듭니다.
6. 선택용 작업에서 후보를 다시 실행하고, 현재 점수보다 높을 때만 채택합니다.

2단계에서 모은 작업 기록을 논문과 문서에서는 **실행 궤적(trajectory)**이라고 부릅니다.
이름은 낯설지만, 에이전트가 무엇을 읽고 어떤 도구를 썼으며 결과가 어땠는지
모아 둔 기록입니다.

여기서 **텍스트 학습률**은 어려운 이름과 달리 한 번에 적용할 최대 편집 개수입니다.
현재 기본 설정은 처음에 최대 4개를 적용하고, 학습이 진행되면 최소 2개까지
줄입니다. 한꺼번에 설명서를 크게 고쳤다가 잘 작동하던 규칙까지 사라지는 일을
줄이려는 장치입니다.

`훈련 작업의 실행 궤적 -> 편집 후보 -> 병합·순위화 -> 제한된 후보 스킬 -> 선택용 작업의 재평가 -> 상승 시 채택, 동점·하락 시 거절`

거절한 편집도 같은 학습 회차 안에서는 실패 기록으로 다시 보여 줍니다. 비슷한
수정을 계속 제안하지 않게 하려는 장치입니다. 학습이 끝나면 사용자는 가장
점수가 높았던 `best_skill.md`만 가져다 쓰면 됩니다. 거절 기록과 편집에 쓴
옵티마이저 모델은 실제 업무에 함께 배포하지 않습니다.

### 0.50 동점까지 거절한 SkillOpt 검증 게이트

문서의 설명이 실제 코드 경계와 맞는지 확인하기 위해 2026년 7월 29일
[공식 저장소](https://github.com/microsoft/SkillOpt)의 커밋 `8304e6c`를
내려받았습니다. Apple Silicon macOS 26.5.2와 Python 3.12.13 격리 환경에서
현재 소스를 설치했습니다. 이 검증은 모델 API를 호출하지 않고 저장소 테스트와
순수 함수인 게이트 로직만 실행했습니다.

게이트의 현재 점수를 0.50으로 고정하고 후보 점수 세 개를 한 번씩 넣었습니다.
점수가 높을수록 좋은 조건이며, 후보가 현재 값을 엄격히 넘어야 성공으로
판정했습니다.

| 후보 점수 | 게이트 판단 | 실행 뒤 현재 점수 |
|---:|---|---:|
| 0.49 | `reject` | 0.50 |
| 0.50 | `reject` | 0.50 |
| 0.51 | `accept_new_best` | 0.51 |

하락한 후보뿐 아니라 동점도 거절했고, 0.01이라도 높아진 후보만 새 최선으로
채택했습니다. 공식 게이트 단위 테스트 22개도 모두 통과했습니다. 그럴듯해
보인다는 이유로 옆걸음 수정을 쌓지 않는다는 설계가 실제 함수에 그대로
반영돼 있었습니다.

전체 테스트에서는 한 가지 흥미로운 실패가 먼저 나왔습니다. 기본 macOS 임시
경로로 실행한 결과는 555개 통과, 6개 건너뜀, 2개 실패였습니다. 두 실패는
SkillOpt-Sleep의 Superpowers overlay 통합 테스트에서 나왔습니다. 테스트가
`/var/folders/...`와 그 실제 경로인 `/private/var/folders/...`를 서로 다른
작업공간으로 판단했습니다.

임시 루트를 실제 경로인 `/private/tmp`로 지정하고 같은 커밋을 다시 실행하자
**557개 통과, 6개 건너뜀**으로 끝났습니다. 이번 결과가 확인한 범위는 핵심
게이트와 저장소 자동 테스트까지입니다. 첫 실행의 macOS 경로 호환 문제나
실제 모델 벤치마크까지 통과했다고 넓혀 말할 수는 없습니다.

### 공식 성능 뒤의 최대 2억 1,380만 학습 토큰

연구팀은 6개 벤치마크와 7개 대상 모델을 직접 채팅·Codex·Claude Code에서
평가해 52개 조합을 만들었습니다. [논문 v2](https://arxiv.org/abs/2605.23904)는
SkillOpt가 이 52개 조합에서 모두 최고 또는 공동 최고였다고 보고합니다.

GPT-5.5의 no-skill 기준과 비교한 평균 향상은 직접 채팅 `+23.5%p`, Codex
`+24.8%p`, Claude Code `+19.1%p`였습니다. 이는 정확도 같은 점수의
절대 퍼센트포인트 차이입니다. 예를 들어 50%에서 60%가 됐다면 10% 증가가
아니라 `+10%p`로 읽습니다.

이 수치는 연구팀이 같은 논문에서 보고한 결과이며, 이번 글에서 52개 실험을
독립 재현한 값은 아닙니다. 더구나 벤치마크에는 정답 일치, 스프레드시트 셀
검사, 문서 질의응답처럼 비교적 채점 기준을 만들기 쉬운 작업이 포함됐습니다.
자유로운 기획이나 문체 평가에서도 같은 폭이 나온다고 예상해서는 안 됩니다.

배포 파일이 작다는 설명도 학습이 싸다는 뜻은 아닙니다. 논문의 GPT-5.5 사례
6개에서 최종 스킬은 379~1,995토큰, 실제로 채택된 편집은 1~4개였습니다.
반면 학습에는 벤치마크별로 2,080만~2억 1,380만 토큰이 쓰였습니다. 최적화가
끝난 뒤에는 옵티마이저 모델을 다시 호출하지 않지만, 그 통과본을 고르는
과정에는 여러 번의 대상 모델 실행과 검증 비용이 필요합니다.

### 직접 학습과 SkillOpt-Sleep은 쓰임이 다른 두 기능

공식 문서는 같은 저장소 안의 연구 엔진과 `SkillOpt-Sleep`을 별도
워크플로로 구분합니다.

- **연구 엔진**: 사용자가 학습용·선택용·시험용 문제와 채점 방법을 직접
  준비하면, 검증을 통과한 `best_skill.md`를 만듭니다. 앞의 가상 예시를 실제
  데이터로 실행하는 기능입니다.
- **SkillOpt-Sleep**: 지원하는 코딩 에이전트의 지난 작업 기록을 살펴 반복
  패턴을 찾고, 사용자가 검토할 스킬·메모리를 제안합니다. 아직 변경 가능성이
  큰 초기 기능입니다.

처음 원리를 확인하려면 연구 엔진의 소스 테스트가 가장 단순합니다. 2026년
7월 29일 기준 공개 패키지는 0.2.0이고 Python 3.10 이상이 필요합니다.
저장소의 config와 테스트까지 쓰려면 다음처럼 소스 체크아웃을 설치합니다.

```bash
git clone https://github.com/microsoft/SkillOpt.git
cd SkillOpt
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e ".[dev]"
python -m pytest tests/test_gate.py -q
```

실제 학습은 문제 묶음과 채점 방법, 업무를 수행할 모델, 스킬을 편집할 모델을
정한 다음 시작해야 합니다. 공식 SearchQA 예제는 선택 설치 항목을 추가하고,
저장소가 제공하는 문제 목록을 실제 예제 파일로 만든 뒤 실행합니다.

```bash
python -m pip install -e ".[searchqa]"
python scripts/materialize_searchqa.py
python scripts/train.py \
  --config configs/searchqa/default.yaml \
  --out_root outputs/searchqa_first_run
```

이 명령에는 선택한 모델의 API 인증과 호출 비용이 필요합니다. 아래 설정
차이는 논문 수치까지 재현하려는 독자만 확인하면 됩니다. 논문에서 공개한
중간 저장본은 `slow_update_gate_with_selection: true`를 썼습니다. 현재
`main` 브랜치의 기본값은 `false`입니다.

SkillOpt-Sleep은 더 신중하게 시작할 필요가 있습니다. 실제 모델 API를 쓰면
과거 세션에서 추린 내용이 선택한 모델 공급자에게 전송될 수 있습니다.
민감하지 않은 프로젝트에서 가짜 모델인 `mock`이나 검토 가능한 작업 파일로
전송 범위를 먼저 확인하세요. 자동 반영하지 말고, 임시 보관된 제안을 사람이
읽은 뒤 채택하는 단계도 남겨 두는 편이 안전합니다.

### SkillOpt는 자동 채점할 수 있는 반복 업무에 적합

앞의 버그 수정 예시처럼 다음 조건을 만족할 때 SkillOpt를 검토할 만합니다.

- 같은 종류의 작업이 반복되고 개선한 스킬을 여러 번 재사용할 수 있습니다.
- 정답 일치, 실행 테스트, 파일 비교처럼 성공 여부를 일관되게 채점할 수 있습니다.
- 규칙을 만드는 학습 사례와 채택을 판단하는 별도 사례를 나눌 수 있습니다.
- 잘못된 스킬 한 줄의 비용이 여러 번의 검증 호출보다 큽니다.

반대로 한 번만 할 작업이나 취향이 핵심인 결과물에는 맞지 않습니다. 정답이
자주 바뀌거나 민감한 실행 기록을 외부 모델에 보낼 수 없는 환경에도 그대로
적용하기 어렵습니다. 이때는 최적화 횟수를 늘리기보다 무엇을 성공으로 볼지
먼저 정하는 편이 중요합니다.

SkillOpt를 시험한다면 처음부터 개인 세션 전체를 Sleep에 연결하지 마세요.
버그 수정처럼 반복되는 작업 하나와 자동 판정 가능한 작은 문제 묶음부터 고르는
편이 좋습니다. 훈련용 실패를 고쳤다는 사실보다 **처음 보지 않은 별도 문제에서도 성공 개수가 늘어나는지**를
먼저 확인해 보세요. 결국 SkillOpt의 성능은 스킬을 써 주는 모델만큼이나,
잘못된 개선을 막는 채점 기준에서 시작됩니다.
