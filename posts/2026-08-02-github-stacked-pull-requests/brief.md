# 기획: GitHub Stacked Pull Request 사용법, 큰 변경을 작은 PR로 쌓는 순서

## 분류와 독자

- 상위 카테고리: `Log`
- 하위 카테고리: `개발 · 디지털`
- 한 명의 독자: 큰 기능을 여러 PR로 나누고 싶지만 종속 브랜치의 base와 rebase 관리가 부담스러운 GitHub 사용자
- 검색 의도: GitHub stacked pull request가 무엇인지, 기존 PR과 무엇이 다른지, 어떻게 시작하는지 확인
- 독자가 이미 아는 것: 일반적인 브랜치 생성, 커밋, pull request 생성 흐름
- 독자가 모른다고 가정할 것: stack의 top·bottom, 각 PR의 base 연결 방식, GitHub의 새 stack 객체와 병합 규칙

## 글의 중심

- 독자가 기억할 한 문장: GitHub Stacked Pull Request는 큰 변경을 의존 순서대로 연결된 작은 PR로 나누고, 각 레이어는 따로 리뷰하면서 병합·rebase 관리는 GitHub와 `gh stack`이 맡도록 만든 기능입니다.
- 낯선 주제를 붙잡아 줄 익숙한 장면: 하나의 거대한 PR과 수동으로 base를 바꾸며 유지하던 종속 PR 묶음
- 가장 쉬운 첫 행동: 공식 변경 로그의 공개 범위를 확인한 뒤, 테스트 저장소에서 GitHub CLI 확장 `github/gh-stack`을 설치해 두 레이어짜리 스택을 만들어 봅니다.
- 이 글이 답하지 않는 범위: 사용자의 실제 저장소·조직 정책에서 기능을 활성화하거나 병합을 실행하지 않으며, 성능 향상이나 리뷰 시간 단축을 독립 측정하지 않습니다.
- 가장 정직한 한계 또는 반론: 2026-08-02 기준 public preview라 UI와 명령이 바뀔 수 있고, merge queue 지원은 순차 배포 중이므로 저장소마다 보이는 상태가 다를 수 있습니다.

## dev.log만의 근거

- first-party contribution: Codex가 2026-08-02 인앱 브라우저에서 GitHub 공식 변경 로그를 직접 열고 대표 화면, CLI 흐름, 스택 맵, 병합 UI를 캡처했습니다. 공식 문서와 `github/gh-stack` 저장소를 대조해 도입 판단표와 실행 순서를 재구성했습니다.
- 실제 실행 주체: `Codex`
- 보존할 원자료: `artifacts/captures/raw/*.jpg`, `artifacts/sources/official-source-snapshot.md`, `media.json`
- 기존 글 또는 시리즈 연결: 개발 도구와 GitHub 워크플로를 다루는 `Log > 개발 · 디지털` 글
- 다른 블로그 이름으로 바꿔도 성립하는 부분: 공식 기능 정의 자체. dev.log의 차이는 캡처 원본·해시·확인 시점·테스트하지 않은 범위를 함께 남긴 점입니다.

## 설명 순서

| 순서 | 독자가 먼저 알아야 할 것 | 다음 내용과의 연결 |
|---|---|---|
| 1 | stack은 같은 저장소 안의 종속 PR 두 개 이상이며, 아래 PR부터 `main`에 연결됩니다. | 왜 각 레이어의 diff만 따로 볼 수 있는지 이해합니다. |
| 2 | 웹과 CLI로 만들 수 있지만 가장 짧은 반복 작업은 `gh stack` 확장입니다. | 실제 명령과 필수 조건으로 이어집니다. |
| 3 | 병합은 bottom-up이며, 위 PR을 병합하면 아래 레이어가 함께 들어갑니다. | 기존 보호 규칙, rebase, preview 한계를 확인합니다. |

## 중앙 판단 사슬

`큰 변경 -> 의존 순서대로 브랜치 분리 -> 각 PR의 base를 바로 아래 브랜치로 연결 -> 레이어별 리뷰·체크 -> 아래부터 일부 또는 전체 병합`

## 보조 인포그래픽 판단

- 결정: `없음`
- 한눈에 보여 줄 관계: `main <- auth <- api <- frontend`
- 글이나 표만으로 충분하지 않은 이유: 해당 없음. 공식 페이지의 stack map 캡처와 간단한 코드 블록·표가 같은 관계를 이미 보여 줍니다.
- 유형: `과정`
- 핵심 설명 뒤 권장 위치: 해당 없음
- 추가 이미지가 있다면 각 이미지가 답할 서로 다른 질문: 공식 페이지 캡처 네 장이 출시 사실, 생성, 리뷰, 병합을 각각 담당합니다.

## 독자가 이어서 물을 질문

- 중간 레이어만 병합하면 위 PR은 어떻게 되나요?
- 외부 fork나 GitHub Desktop에서도 쓸 수 있나요?
- signed commit과 merge queue를 쓰는 저장소에서 무엇을 확인해야 하나요?
