공공데이터 목록에는 흥미로운 이름이 많지만, 승인 뒤 어떤 응답이 오는지는 설명만으로 감을 잡기 어렵습니다. 이번에는 사용자가 승인과 키 입력을 마친 뒤, Codex에서 디지털융합플랫폼의 **전국 화재 현황 API**를 호출하고 응답을 검산했습니다.

응답에는 전국 화재 기록 29만여 건과 화재 유형, 출동·진화 시각, 발화 원인, 피해, 기상 등 62개 상세 필드가 담겨 있었습니다. 다만 2026년 8월 7일에 확인한 최신 화재 접수는 8월 2일이었습니다. 실시간 관제용 스트림이라기보다 며칠 간격으로 묶여 들어오는 분석용 데이터에 가까웠습니다.

### 흩어진 데이터를 찾는 API 마켓

[디지털융합플랫폼 데이터·API 마켓](https://portal.koreaconnect.kr/market/mk/getMkDigitStore)은 정부와 기업에 흩어진 데이터파일과 API를 분야별로 찾아볼 수 있는 곳입니다. 2026년 8월 7일 화면에는 전체 디지털자원 113,389건, 오픈API 12,973건이 표시됐습니다. 숫자는 계속 바뀔 수 있으므로 현재 규모를 보여 주는 시점값으로 보는 편이 맞습니다.

처음부터 코드를 작성할 필요는 없습니다. 마켓에서 분야를 고르고 설명을 읽는 것만으로 어떤 재료가 있는지 빠르게 훑을 수 있습니다.

| 분야 | 화면에서 확인한 API 예시 | 만들어 볼 수 있는 것 |
|---|---|---|
| 재난안전 | 전국 화재·구급·119 신고·구조 현황 | 지역별 사건 추이, 출동 시간 분석 |
| 교통물류 | 주유소 가격, 주차장 기본 정보, 실시간 주차 가능 정보 | 주변 시설 지도, 가격·혼잡 비교 |
| 환경생태기상 | 현재 날씨, 3시간 간격 5일 예보 | 날씨 대시보드, 일정 알림 |
| 건강의료복지 | 의약품개요정보 | 제품명 기반 복약정보 검색 |
| 기업무역 | 행정동별 업종별 상권지수 | 동네·업종별 상권 탐색 |

목록에 보인다고 모두 같은 조건으로 바로 호출되는 것은 아닙니다. 각 상세 페이지에서 제공기관, 요청 방식, 필드와 라이선스를 확인하고 필요한 API에 사용신청을 해야 합니다. 이 글에서는 여러 항목 중 소방청이 제공하는 전국 화재 현황 하나만 실제 호출했습니다.

### 전국 화재 현황을 POST로 호출

[전국 화재 현황 상세 페이지](https://portal.koreaconnect.kr/market/mk/getMkApiDetail?drsTcd=02&drsno=77a018d8298c4921932ea8b51f3c1598)에서 확인한 요청 방식은 `POST`입니다. 발급받은 이용자 키는 `api_user_key_id` 헤더에 넣고, 페이지와 정렬 조건은 쿼리 문자열로 전달합니다.

아래처럼 키를 환경 변수에 담으면 명령 기록에 값을 직접 적는 일을 줄일 수 있습니다.

```bash
export KOREACONNECT_API_KEY='발급받은 API 이용자 키 아이디'

curl -X POST \
  'https://api.koreaconnect.kr/01/1/2605060927592107314KFSBDP/SAFETY/fsdpApi/rest/v1/fire-incidents?page=1&size=5&sort=rcptDt,desc' \
  -H "api_user_key_id: ${KOREACONNECT_API_KEY}"
```

처음에는 `size=1`이나 `size=5`로 구조부터 보는 편이 안전합니다. 명세상 한 페이지의 최대 크기는 100건입니다.

| 변수 | 의미 | 처음 넣어 볼 값 |
|---|---|---|
| `page` | 페이지 번호 | `1` |
| `size` | 페이지당 건수, 최대 100 | `5` |
| `q` | 여러 컬럼의 부분일치 검색 | 필요한 단어가 있을 때만 |
| `sort` | `필드명,asc/desc` 정렬 | `rcptDt,desc` |

헤더를 빼고 같은 URL을 호출했을 때는 `401`과 `유효하지 않은 이용자 서비스 키`가 돌아왔습니다. URL이 틀린 것이 아니라 인증 단계에서 막힌 경우입니다. 키를 쿼리에 옮기기보다 헤더 이름과 승인 상태를 먼저 확인해야 합니다.

### 등록일 첫 행이 최신 화재가 아니었던 이유

인증 요청은 `200 OK`와 JSON을 반환했습니다. `total`은 295,105였고, 응답에는 페이지 정보 7개와 화재 한 건을 설명하는 상세 필드 62개가 있었습니다.

처음에는 등록일을 뜻하는 `gtrRegDt`를 내림차순으로 정렬했습니다. 첫 행은 8월 2일 파주시 차량 화재였습니다. 하지만 상위 여러 행이 모두 같은 등록 시각을 갖고 있어, 첫 행이 실제로 가장 늦게 발생한 화재인지는 알 수 없었습니다.

접수일 `rcptDt`로 다시 정렬하자 결과가 달라졌습니다.

| 확인 항목 | 관찰값 |
|---|---|
| API 확인 시점 | 2026-08-07 23:03 KST |
| 최신 화재 접수 | 2026-08-02 20:38, 경기도 용인시 기흥구 |
| 화재 유형 | 건축·구조물 |
| 인명 피해 | 사망 0명, 부상 0명 |
| 해당 묶음의 등록 시각 | 2026-08-04 06:31:19 KST |

확인 시점과 최신 접수 사이에는 약 5일, 등록 시각과도 약 3일의 차이가 있었습니다. 상위 행들은 동일한 등록 타임스탬프를 공유했습니다. 이 두 가지를 함께 보면 사건이 생길 때마다 한 건씩 들어오는 실시간 스트림보다는 **자료를 모아 갱신하는 배치형 API**에 가까워 보입니다.

다만 한 번의 관찰로 “항상 3일마다 갱신된다”고 말할 수는 없습니다. 공식 명세에서 고정 갱신 주기나 SLA를 확인하지 못했기 때문입니다. 정확한 표현은 2026년 8월 7일 확인에서 3~5일의 시차가 관찰됐다는 정도입니다.

### 3~5일 시차가 바꾼 활용 방향

며칠의 시차는 실시간 알림에는 치명적이지만, 장기 분석에서는 받아들일 수 있는 조건입니다. 전국 단위로 모으기 어려운 사건 기록을 같은 구조로 내려받을 수 있다는 점이 이 데이터의 강점입니다.

| 사용 목적 | 적합도 | 이유 |
|---|---|---|
| 실시간 화재 알림·관제 | 낮음 | 이번 확인에서는 최신 접수가 약 5일 늦었음 |
| 최근 화재 통계 | 조건부 | 마지막 갱신 시각을 함께 표시해야 함 |
| 지역·시설별 장기 추이 | 높음 | 전국 기록과 공통 필드가 있음 |
| 발화 원인·착화물 탐색 | 높음 | 원인, 열원, 기기, 착화물 분류가 제공됨 |
| 데이터 분석·API 학습 | 높음 | 검색, 정렬, 페이지네이션을 작은 요청으로 연습 가능 |

날짜를 고를 때는 특히 주의해야 합니다. `gtrRegDt`는 플랫폼에 등록된 시각이고, `rcptDt`는 화재가 접수된 시각입니다. 최신 사건이 필요하면 업무 의미에 맞는 날짜 필드를 정렬해야 합니다. 같은 등록 시각 안에서 첫 행만 보고 최신이라고 판단하면 이번 확인처럼 다른 사건을 고를 수 있습니다.

### 화재 62개 필드가 여는 분석 질문

화재 한 건에는 단순한 발생 지역보다 훨씬 많은 정보가 들어 있습니다.

- 접수·출동·현장도착·초기진화·완전진화·복귀 시각으로 대응 흐름을 볼 수 있습니다.
- 시도·시군구·소방서·119안전센터와 현장 거리를 지역 분석에 쓸 수 있습니다.
- 화재 유형, 시설 분류, 건물 구조·면적·층수로 장소별 특성을 나눌 수 있습니다.
- 발화 열원·요인·기기·최초 착화물을 묶어 원인 분포를 살펴볼 수 있습니다.
- 사망·부상·인명피해와 재산피해로 피해 규모를 비교할 수 있습니다.
- 기온·습도·풍속·풍향을 사건 기록과 함께 탐색할 수 있습니다.

이 필드들을 함께 그렸다는 이유만으로 인과관계를 주장할 수는 없습니다. 습도와 화재 건수의 움직임이 비슷해도 데이터 누락, 계절, 시설 종류와 지역 차이를 먼저 확인해야 합니다.

빈 값도 자연스럽게 섞여 있습니다. 차량 화재 행에서는 건물 연면적이나 층수 같은 필드가 `null` 또는 빈 문자열이었습니다. 모든 필드를 무조건 숫자로 바꾸기보다 화재 유형에 따라 적용되지 않는 값인지, 실제 누락인지 구분하는 전처리가 필요합니다. 재산피해금액처럼 명세에서 단위를 확인하지 못한 값은 출처에 문의하기 전까지 금액 해석을 미루는 편이 안전합니다.

### 1건부터 확인할 순서

처음부터 29만 건을 모두 내려받을 필요는 없습니다.

1. [데이터·API 마켓](https://portal.koreaconnect.kr/market/mk/getMkDigitStore)에서 관심 분야와 설명을 둘러봅니다.
2. [전국 화재 현황 상세 페이지](https://portal.koreaconnect.kr/market/mk/getMkApiDetail?drsTcd=02&drsno=77a018d8298c4921932ea8b51f3c1598)처럼 각 API의 명세에서 요청 메서드, 인증 헤더, 필수 변수와 응답 필드를 확인합니다.
3. 승인 뒤 `size=1`로 호출해 `total`과 `items` 구조부터 봅니다.
4. 등록일이 아니라 분석 목적에 맞는 사건 날짜로 최신 행을 다시 정렬합니다.
5. 데이터를 저장할 때 API 호출 시각과 마지막 사건 시각을 함께 남깁니다.
6. 빈 값과 단위가 불명확한 필드를 확인한 뒤 필요한 범위만 페이지별로 수집합니다.

이 순서라면 대시보드를 만들기 전에 데이터가 질문에 맞는지 먼저 판단할 수 있습니다. 최신성이 중요한 서비스라면 다른 실시간 소스가 필요하고, 장기 추이나 원인 분포를 보고 싶다면 이 API부터 실험해 볼 만합니다.

전국 화재 현황 외에도 같은 마켓에는 구급·구조·119 신고, 주차장, 주유소 가격, 날씨, 의약품과 상권 데이터가 있습니다. 평소에는 구하기 어려운 자료를 한 페이지씩 열어 보고, 작은 질문 하나를 정해 JSON 몇 건부터 받아보는 것만으로도 꽤 재미있는 프로젝트가 시작됩니다.
