# 기획: 공공데이터 API 활용기, 전국 화재 현황 29만 건을 받아보니

## 분류와 독자

- 상위 카테고리: `Log`
- 하위 카테고리: `개발 · 디지털`
- 한 명의 독자: 공공데이터로 작은 분석이나 토이 프로젝트를 해보고 싶지만
  어떤 데이터가 있고, 승인 뒤 실제 응답이 어느 정도인지 모르는 일반 개발자
- 검색 의도: `공공데이터 API`, `공공데이터 API 활용`, `전국 화재 현황 API`를
  검색해 시작 경로와 실제 데이터 범위, 갱신 한계를 확인
- 독자가 모른다고 가정할 내용: 디지털융합플랫폼 데이터·API 마켓의 정체,
  사용신청과 키 발급, POST 호출 방식, `rcptDt`와 `gtrRegDt`의 차이
- 익숙한 기준: 지도나 표로 보기 어려운 전국 단위 사건 기록을 JSON으로 받아
  지역·시간·원인별로 정리하는 작은 데이터 프로젝트
- 가장 쉬운 시작: 로그인 없이 마켓에서 분야와 데이터 설명을 둘러본 뒤,
  필요한 API 하나만 사용신청하고 1건을 조회

## 글의 중심

- 독자가 기억할 한 문장: 전국 화재 현황 API는 29만여 건과 62개 상세 필드를
  손쉽게 꺼낼 수 있지만, 2026년 8월 7일 확인에서는 최신 접수가 8월 2일이고
  8월 4일에 묶음 등록돼 실시간 스트림보다는 배치 분석 자료에 가까웠습니다.
- 낯선 주제를 붙잡아 줄 익숙한 장면: 뉴스 기사나 개별 기관 자료를 모으지 않고
  전국 화재 기록을 한 번의 API 호출로 받는 장면
- 가장 짧은 성공 경로: 마켓 검색 -> 상세 명세 확인 -> 사용신청과 승인 ->
  키를 헤더에 넣어 1건 호출 -> 도메인 날짜와 등록 날짜를 따로 확인
- first-party contribution: 사용자가 발급받은 키로 Codex가 실제 POST 요청을
  수행해 200 OK, 295,105건, 최신 접수일, 동일한 묶음 등록 시각을 확인하고
  원시 JSON을 보존
- 가장 정직한 한계: 한 시점의 관찰만으로 고정 갱신 주기나 SLA를 확정할 수
  없습니다. `배치형`은 상위 최신 행들이 동일한 등록 시각을 가진 점과 사건일과
  등록일 사이의 시차에 근거한 관찰입니다.
- 이 글이 답하지 않는 범위: 전수 데이터 품질 감사, 누락률, 필드 단위 정의,
  재산피해금액의 단위, 고정 갱신 주기, 다른 API의 인증 호출 성공 여부
