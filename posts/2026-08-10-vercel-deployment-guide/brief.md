# 기획: Vercel 사용법, GitHub 첫 배포부터 환경 변수·도메인까지

## 분류와 독자

- 상위 카테고리: `Log`
- 하위 카테고리: `개발 · 디지털`
- 한 명의 독자: GitHub 저장소는 있지만 웹 프로젝트를 외부에 배포해 본 적이 없는 입문 개발자
- 검색 의도: Vercel이 무엇인지 이해하고, 대시보드에서 저장소를 연결해 첫 배포와 도메인 설정까지 끝내고 싶음
- 독자가 이미 아는 것: GitHub에 코드를 올리고 브랜치에 커밋을 푸시하는 기본 흐름

## 글의 중심

- 독자가 기억할 한 문장: Vercel의 첫 배포는 Production이며, 그 뒤에는 `main`은 운영, 다른 브랜치는 미리보기로 나누는 것이 가장 쉬운 흐름입니다.
- 낯선 주제를 붙잡아 줄 익숙한 장면: 로컬에서는 열리지만 다른 사람에게 보여 줄 주소가 없는 웹 프로젝트
- 이 글이 답하지 않는 범위: 특정 프레임워크의 세부 빌드 최적화, 요금제 비교, 대규모 운영 아키텍처, 계정별 실제 화면 재현
- 가장 정직한 한계 또는 반론: 화면 이름과 정책은 바뀔 수 있으며, 이 글은 2026-08-10 Vercel 공식 문서를 기준으로 한 source-based 안내입니다.

## dev.log만의 근거

- first-party contribution: 공식 문서의 배포·환경·도메인·권한 규칙을 초보자의 실제 막힘 순서로 재배열한 `배포 전 6문항`과 `증상별 첫 확인 지점` 결정표
- 실제 실행 주체: `Codex`
- 보존할 원자료: `artifacts/sources/`의 공식 문서 HTML 스냅숏 10개, 공식 OG 이미지 1개, 공식 UI 스크린샷 3개
- 기존 글 또는 시리즈 연결: 개발 도구 사용법과 문제 해결을 다루는 `Log > 개발 · 디지털` 클러스터
- 다른 블로그 이름으로 바꿔도 성립하는 부분: 공식 기능 설명. 이를 줄이고, dev.log의 검증 원칙에 맞춘 확인 순서와 한계 표시에 무게를 둡니다.

## 설명 순서

| 순서 | 독자가 먼저 알아야 할 것 | 다음 내용과의 연결 |
|---|---|---|
| 1 | Vercel은 저장소의 코드를 빌드해 URL로 만드는 배포 플랫폼 | 저장소 연결이 첫 설정이 되는 이유 |
| 2 | 첫 배포는 Production이고 이후부터 브랜치별 규칙이 적용된다는 예외 | 안전한 수정·검토 흐름 |
| 3 | 환경 변수와 도메인은 배포 뒤 별도로 확인해야 함 | 운영 전 체크리스트와 장애 진단 |

## 중앙 판단 사슬

`Git 커밋 -> Vercel이 프레임워크·빌드 설정으로 빌드 -> 첫 배포는 Production -> 이후 브랜치에 따라 Preview/Production 판단 -> 고유 URL 또는 사용자 도메인 제공`

## 보조 시각 자료 판단

- 인포그래픽 결정: `없음`
- 인포그래픽 없이 설명할 관계: 첫 Production 예외와 이후 Git 브랜치별 Preview/Production 연결은 3열 표와 단계 목록으로 충분합니다.
- 공식 UI 스크린샷 결정: `3개`
- 스크린샷 1이 답할 질문: 새 프로젝트를 만드는 메뉴는 어디에 있는가?
- 스크린샷 2가 답할 질문: 환경 변수의 적용 환경과 Key·Value는 한 화면에서 어떻게 나누는가?
- 스크린샷 3이 답할 질문: 도메인 DNS 설정에서 어떤 Type·Name·Value를 옮겨야 하는가?
- 배제한 화면: 저장소 목록은 `Import`라는 한 동작만 보여 주므로 텍스트 설명으로 충분하며, 독자의 업로드 부담을 줄이기 위해 추가하지 않습니다.
