# 기획: GitHub 장애 대응, 코드 밖의 리뷰·빌드·배포까지 점검하는 법

## 분류와 독자

- 상위 카테고리: `Log`
- 하위 카테고리: `개발 · 디지털`
- 한 명의 독자: GitHub를 원격 저장소와 Pull Request 용도로 쓰지만 장애 시 무엇이 멈추는지는 정리하지 않은 개발자 또는 작은 팀의 실무자
- 검색 의도: GitHub 장애가 나면 어떤 업무가 멈추며 무엇을 백업하거나 분리해야 하는지 알고 싶음
- 독자가 이미 아는 것: `clone`, `commit`, `push` 같은 기본 Git 작업과 Pull Request의 용도
- 독자가 아직 모르는 것: Git 저장소 사본과 GitHub 협업 메타데이터·Actions 제어면·릴리스 자산의 복구 범위가 다르다는 점

## 글의 중심

- 독자가 기억할 한 문장: GitHub 장애 대응은 서비스 이전부터 결정할 일이 아니라, 코드·협업 기록·자동화·프로젝트 입구를 나눠 업무 연속성을 확인하는 일입니다.
- 낯선 주제를 붙잡아 줄 익숙한 장면: 로컬 코드는 남아 있는데 PR 검토, CI, 릴리스가 한꺼번에 멈추는 근무 시간의 장애
- 가장 쉬운 시작: `GitHub가 8시간 멈추면 꼭 계속되어야 하는 일은 무엇인가`를 먼저 한 줄로 적고 네 층의 의존성 표에 배치
- 첫 화면 답: Git은 분산 저장소이지만 GitHub는 리뷰·이슈·자동화·릴리스까지 묶은 포지이므로 코드 미러만으로는 업무가 복구되지 않음
- 이 글이 답하지 않는 범위: GitHub·GitLab·Codeberg·Forgejo의 전체 기능 및 비용 비교, 특정 서비스로의 실제 마이그레이션 절차, GitHub 장애 원인에 대한 독자적 추정
- 가장 정직한 한계 또는 반론: GitHub의 네트워크 효과와 통합 기능을 다시 만드는 비용이 장애 비용보다 클 수 있으므로 모든 팀에 이전을 권하지 않음
- 테스트 경계: 제품 UI를 직접 조작하거나 장애를 재현하지 않음. 공식 장애 보고서와 공식 문서를 바탕으로 운영 판단표를 설계함

## dev.log만의 근거

- first-party contribution: 공개 기능을 나열하지 않고 `업무 산출물 -> GitHub 표면 -> 코드 미러 복구 여부 -> 최소 대체 경로`로 연결한 4층 의존성 점검표와 3문항 결정 규칙
- 실제 실행 주체: `Codex`
- 보존할 원자료: 공식 GitHub Status 장애 기록, Git·GitHub 공식 문서 URL, 주장별 근거와 한계가 담긴 `evidence.md`
- 기존 글 또는 시리즈 연결: `posts/2026-08-02-github-stacked-pull-requests/`의 PR 협업 설명과 주제상 연결되지만, 이번 글은 장애와 운영 의존성을 다룸
- 다른 블로그 이름으로 바꿔도 성립하는 부분: 공식 기능 설명은 성립함. 네 층의 복구 우선순위와 `긴급 릴리스부터 분리` 판단이 dev.log의 검증 중심 기여임

## 설명 순서

| 4 | 긴급 릴리스 경로와 중요한 운영 기록이 가장 먼저 분리할 후보 | 유지·부분 분리·이전 결정을 세 질문으로 마감 |

## 중앙 방법의 판단 사슬

`GitHub가 멈춘 상황 -> 계속되어야 할 업무 산출물 식별 -> Git 저장소/협업 메타데이터/자동화·릴리스/입구·정체성으로 분류 -> 코드 미러만으로 복구되는지 판정 -> 최소 대체 경로와 복구 연습 결정`

## 미디어와 조건부 게이트

- lead 역할: GitHub 홈페이지에서 planning, discussion, code review를 코드 옆에 둔 협업 작업 공간을 보여 주는 사용자 제공 화면
- concept 이미지 역할: GitHub Actions가 저장소 이벤트, 워크플로, job, runner로 이어지는 구조임을 보여 주는 공식 GitHub Docs 다이어그램
- reader-friction screenshot: `없음` - UI 절차 안내가 아니라 운영 의존성 설명이며 화면을 추가해도 독자의 entry point·choice·verification 질문을 더 잘 해결하지 못함
- 생성 hero: `아니요` - 사용자가 제공한 GitHub 홈페이지 화면과 주제에 직접 관련된 공식 정적 다이어그램으로 충분함
- 보조 인포그래픽: `없음` - 네 층의 관계는 짧은 표가 모바일에서 더 읽기 쉽고 업로드 부담도 작음
- 복잡 레이아웃·390px·768px·GIF·두 번째 원격 fetch: `모두 불필요`

## 독자가 이어서 물을 질문

- 자체 호스팅 runner가 있으면 GitHub Actions 장애를 피할 수 있나요?
- GitHub를 떠나지 않고도 의존성을 줄일 수 있나요?
- 무엇부터 분리해야 하나요?
