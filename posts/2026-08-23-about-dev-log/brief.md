# 기획: 블로그 소개

## 분류와 독자

- 상위 카테고리: `Log`
- 하위 카테고리: `개발 · 디지털`
- 한 명의 독자: dev.log를 처음 방문해 이 블로그가 무엇을 다루고 어떤 기준으로 쓰이는지 알고 싶은 독자
- 검색 의도: 운영자 소개, 주제 범위, 글의 신뢰 기준과 문의 방법 확인
- 독자가 이미 아는 것: 블로그 이름과 개별 게시글 한두 편

## 글의 중심

- 독자가 기억할 한 문장: `궁금증에서 출발해 검증으로 닫습니다.`
- 낯선 주제를 붙잡아 줄 익숙한 장면: 인터넷에서 결론은 찾았지만 근거와 적용 범위가 없어 실제 판단에는 쓰기 어려운 경험
- 이 글이 답하지 않는 범위: 운영자의 상세한 이력, 각 게시글의 개별 근거, 법적·의학적 전문 자문
- 가장 정직한 한계 또는 반론: 주제가 넓어 블로그의 초점이 흐려 보일 수 있으므로, 다섯 카테고리의 역할과 공통된 검증 원칙을 분명히 설명한다.

## dev.log만의 근거

- first-party contribution: 2026-08-23 공개 블로그의 실제 카테고리 구조와 새로 추가된 Off.log 첫 글을 직접 확인해 현재 운영 방향을 반영
- 실제 실행 주체: `Codex`
- 보존할 원자료: `artifacts/public-site-review.md`
- 기존 글 또는 시리즈 연결: 기존 공지 `블로그 소개`를 같은 제목으로 전면 개정
- 다른 블로그 이름으로 바꿔도 성립하는 부분: 일반적인 출처 확인 원칙은 다른 블로그에도 적용된다. 다만 dev.log의 다섯 카테고리와 `궁금증에서 출발해 검증으로 닫습니다`라는 운영 문장, 테스트 환경·실패 조건을 함께 남기는 기술 글의 기준을 구체적으로 연결한다.

## 설명 순서

| 순서 | 독자가 먼저 알아야 할 것 | 다음 내용과의 연결 |
|---|---|---|
| 1 | dev.log가 답보다 확인 과정을 중시하는 이유 | 주제가 달라도 하나의 블로그로 묶이는 기준 |
| 2 | Log·Trends·Health·Reflections·Off.log의 역할 | 각 주제를 어떤 방식으로 다루는지 |
| 3 | 출처·테스트·AI 활용·수정 원칙 | 독자가 글을 어느 범위까지 믿고 피드백할 수 있는지 |

## 중앙 판단 사슬

`궁금증 -> 원문·공식 자료 또는 직접 테스트 확인 -> 사실·관찰·해석 구분 -> 한계와 함께 기록`

## 보조 인포그래픽 판단

- 결정: `없음`
- 한눈에 보여 줄 관계: 다섯 카테고리가 하나의 검증 원칙으로 모이는 구조
- 글이나 표만으로 충분하지 않은 이유: 카테고리 소개가 각각 짧고 같은 화면에서 순서대로 읽히므로 별도 도식이 읽기 시간을 줄이지 않는다.
- 유형: `비교`
- 핵심 설명 뒤 권장 위치: 해당 없음
- 추가 이미지가 있다면 각 이미지가 답할 서로 다른 질문: 해당 없음

## 독자가 이어서 물을 질문

- 어떤 주제를 다루나요?
- 정보는 어떤 방식으로 확인하나요?
- AI가 글 작성에 참여하나요?
- 오류를 발견하면 어디로 알려야 하나요?
