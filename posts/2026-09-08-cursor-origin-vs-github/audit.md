## 독자와 글의 뼈대

- 한 명의 독자: Cursor를 쓰며 Origin 때문에 기존 GitHub 저장소를 옮겨야 하는지 궁금한 개발자와 소규모 팀
- 뼈대 문장: Cursor가 Git 저장소와 에이전트 작업을 한곳에 묶는 Origin을 공개했지만 GitHub 미러가 플랫폼 메타데이터 전체를 옮기지 않으므로, 기존 프로젝트는 GitHub를 원본으로 둔 시험부터 시작합니다.
- 첫 화면의 구체적인 상황: Cursor에서 수정한 코드를 GitHub에 push하고 PR을 열던 흐름에 새 코드 저장소 선택지가 등장함
- 긴장: Origin이 GitHub를 대체하는지, 두 서비스를 함께 써야 하는지 구분하기 어려움
- 실용적인 답: 기존 GitHub 프로젝트는 미러, 새 비공개 에이전트 중심 프로젝트는 Origin 단독 시험, 공개·플랫폼 의존 프로젝트는 GitHub 유지
- 근거 경계: 2026-09-08 공식 문서에 명시된 기능을 비교했으며 실제 계정 활성화, 성능, 안정성, 총비용은 시험하지 않음

### 독자 효익 계약

- 독자가 아는 상황: Cursor 수정 뒤 GitHub push·PR을 사용함
- 모르는 내용: Origin이 Git remote 이름인지 별도 서비스인지, GitHub 데이터가 무엇까지 따라오는지
- 한 가지 권고: 기존 프로젝트는 GitHub 원본+Origin 미러부터 시험함
- 유용한 결과: Issues·Actions·비밀값을 잃는 전면 이전을 피하면서 Origin의 에이전트 연결 가치를 확인함
- 의도적으로 제외한 내용: 성능 벤치마크, 보안 인증, 총비용, 대규모 이전 절차

### opening movement

- 상황: Cursor에서 코드를 수정하고 GitHub로 PR을 여는 익숙한 흐름
- 긴장: 자체 코드 저장소 발표가 GitHub 대체를 뜻하는지 혼란스러움
- 답: 기존 프로젝트의 기본 선택은 GitHub가 원본인 Origin 미러
- 근거 경계: 초기 베타의 현재 공식 문서 범위이며 직접 계정과 성능을 시험하지 않음
- 삭제한 초안 표면: `이번 글에서는`, `결론부터 말하면`, 기능 전체를 먼저 나열하는 뉴스형 요약을 사용하지 않음

### AI-template 문장 프레임

- `단순히 GitHub의 대체제가 아니라`라는 대비형 문장을 쓰지 않고, GitHub 미러가 원본을 유지한다는 제품 동작을 직접 설명함.
- `가장 큰 차이는 에이전트에 있습니다`라는 빈 강조를 쓰지 않고, Cursor와 GitHub가 모두 에이전트를 지원한다는 반례 뒤에 기준점의 차이를 제시함.
- `차근차근 살펴보겠습니다`와 section 예고 문장을 모두 제외함.
- `협업은 GitHub, 에이전트는 Origin`이라는 균형 잡힌 구호를 반박하고 프로젝트 원본과 플랫폼 메타데이터로 판단하도록 고침.

- 미러의 `GitHub가 원본`이라는 결론은 미러 section에 한 번 완전하게 설명하고 opening과 closing에서는 선택만 짧게 제시함.

### 보호한 사실과 한계

- Origin 초기 베타와 접근 순차 공개를 유지함.
- GitHub 미러에서 Issues·Actions 워크플로·비밀값이 제외된다는 경계를 유지함.
- GitHub와 Origin이 모두 에이전트 기능을 제공한다는 반례를 유지함.
- `현재 문서에서 확인되지 않음`을 `기능이 없음`으로 강화하지 않음.
- 직접 Origin 계정, 성능, 안정성, 에이전트 결과를 시험하지 않았다는 한계를 공개 기능표와 선택표 가까이에 둠.
