# 기획: Github vs. Cursor Origin, 코드 저장소 비교

## 분류와 독자

- 상위 카테고리: `Log`
- 하위 카테고리: `개발 · 디지털`
- 한 명의 독자: Cursor를 쓰고 있으며 새로 공개된 Origin이 GitHub를 대체하는지, 기존 저장소를 옮겨야 하는지 궁금한 개발자와 소규모 팀
- 검색 의도: Cursor Origin의 정체, GitHub와 겹치는 기능, GitHub 미러링 범위, 도입에 맞는 프로젝트를 빠르게 판단하려는 비교형 검색
- 독자가 이미 아는 것: GitHub가 코드를 올리고 Pull Request를 여는 곳이라는 사실은 알지만 `git forge`, 미러의 원본 관계, 플랫폼 메타데이터의 범위는 모를 수 있음

## 글의 중심

- 독자가 기억할 한 문장: 기존 프로젝트는 GitHub를 원본으로 둔 채 Origin 미러부터 시험하고, 새 비공개 프로젝트에서 Cursor 에이전트가 개발 흐름의 중심일 때만 Origin 단독 호스팅을 검토합니다.
- 낯선 주제를 붙잡아 줄 익숙한 장면: Cursor에서 코드를 수정한 뒤 GitHub에 push하고 PR을 열던 흐름에 새로운 저장소 선택지가 등장한 상황
- 첫 화면의 답: Origin은 Cursor가 만든 Git 저장소 호스팅 서비스이며 GitHub와 저장소·PR 기능이 겹치지만, 초기 베타의 기능 범위와 생태계는 더 좁음
- 가장 쉬운 시작: 중요도가 낮은 기존 GitHub 저장소 하나를 미러링하고 GitHub를 원본으로 유지한 채 코드 탐색과 에이전트 연결만 확인함
- 이 글이 답하지 않는 범위: 실제 Origin 계정 활성화 후기, 대규모 저장소 성능, 장애 복구 수준, 가격 총액, GitHub Enterprise 전체 기능 비교, 보안·규제 적합성 인증
- 가장 정직한 한계 또는 반론: 2026-09-08 현재 Origin은 초기 베타이며 접근이 순차적으로 열리고 문서와 기능이 바뀔 수 있음. 기능표는 공식 문서에 명시된 범위만 비교하며 비공개 로드맵이나 실사용 성능을 추정하지 않음

## dev.log만의 근거

- first-party contribution: Cursor 공식 페이지·문서 7종과 GitHub 공식 페이지·문서 8종을 동일한 10개 판단 항목으로 재분류한 `artifacts/origin-github-feature-matrix.csv`. 기능의 존재만 나열하지 않고 `기존 저장소 미러`, `Origin 단독 호스팅`, `GitHub 유지`의 세 도입 경로로 다시 배열함
- 실제 실행 주체: `Codex`
- 보존할 원자료: `evidence.md`의 주장별 URL·확인일·한계, `artifacts/origin-github-feature-matrix.csv`, Cursor 공식 Origin OG 이미지의 원본 바이트와 SHA-256
- 기존 글 또는 시리즈 연결: `GitHub 장애 대응, 코드 밖의 리뷰·빌드·배포까지 점검하는 법`에서 사용한 `코드 저장소`와 `플랫폼 기능`의 구분을 Origin 도입 판단에 적용함. 해당 글은 아직 공개 URL이 없어 본문 내부 링크는 넣지 않음
- 다른 블로그 이름으로 바꿔도 성립하는 부분: 공식 기능 요약 자체는 성립함. dev.log만의 차이는 같은 항목으로 두 플랫폼을 재분류하고, 미러가 옮기지 않는 Issue·Actions·비밀값까지 포함해 전환 경로를 제안하는 데 있음

## 설명 순서

| 순서 | 독자가 먼저 알아야 할 것 | 다음 내용과의 연결 |
|---|---|---|
| 1 | Origin은 Git remote의 관습적 이름이 아니라 저장소를 보관하고 PR을 다루는 Cursor의 git forge | GitHub와 겹치는 핵심 기능을 비교할 수 있음 |
| 2 | Git 저장소·코드 탐색·PR은 겹치지만 Issues·CI·보안·공개 생태계의 문서화 범위는 다름 | 기존 GitHub 프로젝트를 곧바로 옮기지 않을 이유가 생김 |
| 3 | GitHub 미러는 GitHub를 원본으로 두고 Git 이력·PR만 동기화함 | 독자가 미러, Origin 단독 호스팅, GitHub 유지 중 하나를 고를 수 있음 |

## 2026-09-09 전달력 개정

- 독자가 기억할 판단: 기본 Git 작업은 겹치지만 협업과 자동화를 운영하는 서비스가 다릅니다. 이미 쓰는 GitHub 기능을 유지하면서 Origin의 탐색·PR이 필요할 때 미러를 연결합니다.
- 전개: 공통 Git 작업을 이해한 뒤 GitHub에 쌓인 협업 기록의 의미를 살피고, 양쪽 에이전트 연결을 비교합니다. 이 차이를 이해한 상태에서 미러의 동작과 세 가지 선택을 읽습니다.
- 첫 화면에서는 미러라는 용어와 검증 절차를 먼저 꺼내지 않습니다. 코드와 리뷰를 동기화할 수 있다는 실용적인 답을 주고, 기능 비교표 앞에서 현재 베타 기준임을 밝힙니다.
- 질문별 소유 section: 기본 역할은 `두 서비스가 공유하는 Git 저장소`, 코드 밖의 운영은 `GitHub에 함께 쌓이는 협업 기록`, AI 기능은 `AI 에이전트를 연결하는 방식`, 동기화 범위와 연결 조건은 `GitHub 저장소를 연결하는 미러`, 도입안과 베타 제약은 `프로젝트에 맞는 선택`이 담당합니다.
- 표는 3열로 줄이고, 첫 표는 기능의 차이를, 마지막 표는 독자의 상황과 첫 확인 사항을 비교합니다. 원자료 CSV는 상세 근거로 유지합니다.
- Origin 계정이나 성능을 시험했다는 주장은 계속 제외합니다. API·접근 조건·공개 범위·미러 제외 데이터는 축약 중에도 보존합니다.
