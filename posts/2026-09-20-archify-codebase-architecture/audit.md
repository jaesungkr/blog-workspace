## v2 문체·밀도 검토

### 독자와 첫 화면

- 독자: 처음 맡은 저장소를 빠르게 파악하고 동료에게 설명해야 하는 개발자입니다.
- 이미 아는 것: AI 코딩 에이전트와 아키텍처 그림의 용도는 알지만 Agent Skill과 JSON IR은 모릅니다.
- 첫 화면의 상황: 파일은 많고 최신 구조도는 없으며, AI가 그럴듯하지만 틀린 상자를 만들 수 있습니다.
- 첫 화면의 답: Archify는 에이전트가 쓴 JSON 명세를 검사해 대화형 HTML로 만듭니다.
- 증거 경계: Archify는 코드 의미를 자동으로 완전하게 판정하는 정적 분석기가 아닙니다.
- 제외한 내용: 모델별 코드 이해 정확도, 대형 모노레포 성능, CI 설계, 모든 Viewer 기능은 이 글의 질문을 넓히므로 제외했습니다.

### 제목과 소제목 띠

- 초기 소제목: `Archify가 그림을 만드는 방식` → `직접 실행에서 통과한 것과 막힌 것` → `설치는 한 줄, 요청은 한 질문` → `Mermaid 대신 Archify를 고를 조건` → `검증이 보장하지 않는 것`
- 선택한 소제목: `Archify가 그림을 만드는 방식` → `7개 노드 실험에서 확인한 검증 경계` → `영구 설치와 일회성 실행 중 고르기` → `첫 요청은 API 경로 하나로` → `Mermaid 대신 Archify를 고를 조건` → `저장소 근거가 아키텍처 정답은 아닌 이유`
- 첫 소제목의 역할은 정체 확인, 두 번째는 직접 검증, 세 번째는 설치, 네 번째는 첫 요청, 다섯 번째는 선택, 마지막은 신뢰 경계 판단입니다.
- `통과한 것과 막힌 것`, `보장하지 않는 것`처럼 대상이 흐린 문구를 실제 표본과 경계가 드러나는 표현으로 고쳤습니다. 설치와 프롬프트 설계를 한 소제목에 묶었던 대칭 구조도 두 독자 행동으로 분리했습니다.

### 문장 프레임과 보존 사항

- `이 구조가 주목받는 이유는`이라는 해설형 문장을 `Archify는 AI에게 그림 자체를 맡기지 않습니다`로 바꾸고 바로 역할을 설명했습니다.
- `장점은 A보다 B` 구조를 없애고 실험에서 확인한 사실과 807KB 비용을 연속된 관찰로 적었습니다.
- 한 문장에 설치 대상 네 개와 제품 정의를 함께 넣었던 부분을 제품 정의와 지원 도구로 나눴습니다.
- 보존한 사실: 커밋, Node.js 버전, 9개 검사, 오류·경고 0개, 806,884바이트, 네 뷰포트, 실패 종료 코드와 진단 코드, 설치 명령, 다섯 유형, 저장소 근거의 선택적 성격입니다.
- 보존한 한계: 표본은 수작업으로 작성한 작은 Architecture 입력 1개와 실패 입력 1개이며, 모델별 코드 해석 정확도를 측정하지 않았습니다.
- 출처가 없는 경험, 감정, 대화, 사용자 개인의 실행 경험은 추가하지 않았습니다.
- 실패 입력은 `validate`로만 확인했으므로 “결과물을 만들지 않았다”는 해석을 삭제하고 “검증 단계에서 거부했다”로 좁혔습니다.
- Mermaid 비교는 공식 Flowchart 문서와 GitHub의 Markdown 지원 설명을 추가하고, 링크·클릭 이벤트 가능성을 반영했습니다. 비교표가 직접 성능 시험이 아니라 사용 조건 비교라는 문장도 붙였습니다.
