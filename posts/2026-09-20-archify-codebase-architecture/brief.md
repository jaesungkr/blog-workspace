# 기획: Archify란? AI가 읽은 코드 구조를 검증 가능한 다이어그램으로 만드는 방법

## 분류와 독자

- 상위 카테고리: `Log`
- 하위 카테고리: `개발 · 디지털`
- 한 명의 독자: 처음 맡은 코드 저장소의 구조를 빠르게 파악하고 동료에게 설명해야 하는 개발자
- 검색 의도: Archify가 무엇인지, 어떻게 설치하고 요청하는지, Mermaid와 무엇이 다른지, 결과를 어디까지 믿어도 되는지 알고 싶습니다.
- 독자가 이미 아는 것: AI 코딩 에이전트와 아키텍처 다이어그램의 용도는 알지만 Agent Skill, JSON IR, 검증 프로필은 모릅니다.

## 글의 중심

- 독자가 기억할 한 문장: Archify는 코드 구조를 스스로 발견해 정답을 내는 분석기가 아니라, 에이전트가 작성한 구조 명세를 검사하고 대화형 HTML로 만드는 도구입니다.
- 낯선 주제를 붙잡아 줄 익숙한 장면: 새 저장소를 열었는데 README의 그림은 오래됐고, 파일을 모두 읽기 전에 요청 흐름과 핵심 경계를 설명해야 하는 상황입니다.
- 이 글이 답하지 않는 범위: 다수 모델의 코드 해석 정확도 비교, 대형 모노레포 성능 벤치마크, CI 자동화 설계, 모든 Viewer 기능의 사용법은 다루지 않습니다.
- 가장 정직한 한계 또는 반론: 형식·배치·연결 대상 검증은 강하지만, 에이전트가 중요한 컴포넌트를 빠뜨렸는지까지 자동으로 판단하지는 않습니다. 저장소 근거 검증도 명시적으로 커밋과 파일·줄 범위를 연결한 Architecture 입력에서만 작동합니다.

## dev.log만의 근거

- first-party contribution: Archify main 커밋을 고정하고 한국어 7노드 다이어그램을 직접 작성해 `doctor`, `validate`, `deliver`, `visual-check`를 실행했습니다. 존재하지 않는 노드를 가리키는 실패 입력도 별도로 검증했습니다.
- 실제 실행 주체: `Codex`
- 보존할 원자료: `artifacts/experiment-log.md`, 두 JSON 입력, 전달된 HTML, 브라우저 검사 JSON과 라이트·다크 캡처 4장
- 기존 글 또는 시리즈 연결: AI 코딩 도구의 기능을 소개하는 데서 멈추지 않고, 실제 명령과 실패 입력까지 보존하는 dev.log의 개발 도구 검증 흐름을 잇습니다.
- 다른 블로그 이름으로 바꿔도 성립하는 부분: 공식 기능과 설치법 설명은 일반적인 내용입니다. 정확한 커밋·환경·산출물 해시·실패 진단을 함께 남긴 부분이 dev.log 고유 근거입니다.

## 설명 순서

| 순서 | 독자가 먼저 알아야 할 것 | 다음 내용과의 연결 |
|---|---|---|
| 1 | Archify는 에이전트용 스킬과 로컬 검증·렌더링 도구의 결합입니다. | 자동 정답 생성기로 오해하지 않은 상태에서 실제 처리 과정을 봅니다. |
| 2 | 에이전트가 JSON IR을 쓰고 Archify가 형식·배치·산출물을 검사합니다. | 직접 실행 결과로 검사 범위와 실패 동작을 확인합니다. |
| 3 | 설치보다 한 다이어그램이 답할 질문을 좁히는 일이 중요합니다. | Mermaid와 비교해 맞는 사용 조건과 한계를 결정합니다. |

## 중앙 방법의 계산 또는 판단 사슬

`코드 저장소 또는 시스템 설명 -> 에이전트가 범위를 정하고 JSON IR 작성 -> Archify가 스키마·연결·배치·HTML/SVG 검사 -> 자체 포함 대화형 HTML`

## 보조 인포그래픽 판단

- 결정: `없음`
- 한눈에 보여 줄 관계: 별도 인포그래픽은 만들지 않고, Archify로 직접 생성한 결과 화면이 입력부터 HTML까지의 관계를 보여 줍니다.
- 글이나 표만으로 충분하지 않은 이유: 실제 Viewer의 정보 밀도와 산출물 형태는 결과 화면을 봐야 판단할 수 있습니다.
- 유형: `과정`
- 핵심 설명 뒤 권장 위치: 대표 이미지를 도입부 다음에 둡니다.
- 추가 이미지가 있다면 각 이미지가 답할 서로 다른 질문: 추가 이미지는 없습니다. 검사 수치는 표가 더 정확하고 업로드 부담도 줄어듭니다.
