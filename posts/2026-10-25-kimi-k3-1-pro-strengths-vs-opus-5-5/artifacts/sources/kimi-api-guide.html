    了解 Kimi K3.1 Pro 的 API 调用方式：推理强度、流式输出、视觉输入、工具调用与 100 万 token 上下文。

    ​
    模型简介

    Kimi K3.1 Pro 是全新 K3.1 系列的第一个模型，也是我们迄今能力最强的 3 万亿级参数模型，支持 100 万上下文。K3.1 Pro 在代码、3D 创作、金融研究和其他长程 Agent 能力上的提升尤为显著。 我们同步推出高速版模型 Kimi K3.1 Pro Highspeed，同等智能，输出速度约 2~3 倍。完整模型权重将于 11 月 4 日前发布。

    ​
    持续突破前沿

    在 Kimi K3.1 Pro 的研发中，我们大幅增加了强化学习（RL）环节的算力投入。为了支撑数百个下游领域的大规模联合训练，我们优化了技术栈的每一层，包括 RL 框架、长上下文推理、训练效率、沙箱基础设施、调度系统，以及用于环境质量检查的共享平台等，确保每一份新增的 RL 算力都能转化为稳定、高效的回报。 在代码、Agent 和知识类基准上，K3.1 Pro 达到或接近最强闭源模型的水平。Terminal-Bench 4.0 通过真实环境中资源受限的终端任务考察编程智能体的能力，每项任务均设有严格的专项测试。K3.1 Pro 在此项评估中得分 65.7%，超过 GPT-6 Astra（58.2%），与 Claude Opus 5.5（66.4%）仅有微弱差距。Kimi Code Bench 3.0 Long-horizon 是我们内部的基准测试，覆盖多种工程领域，重点考察编程智能体的多步执行、工具调用和端到端问题解决能力。K3.1 Pro 在此项测试中得分 61.2%，高于 K3 的 55.95%。

    网络安全

    随着 K3.1 Pro 的能力不断提升，我们将更多精力投入到了解其安全能力的来源，以及我们能在多大程度上对其进行管控。为此，我们分析并评估了 K3.1 Pro 的漏洞研究能力，同时在训练过程中实施了针对性控制，在降低潜在滥用风险的同时，保留模型的通用实用性。 识别并移除网络攻防相关数据。在开发过程中，我们观察到随着后训练规模扩大，模型的漏洞研究性能持续提升。追溯这一趋势的来源，我们发现网络攻防相关内容嵌入了中期训练的通用语料中，网络攻防相关任务也存在于强化学习环境组合里。这是使用广泛数据进行训练带来的自然副产品。在内部模型的初步实验中，我们发现若在中期训练和强化学习阶段均不移除相关数据，下游网络攻防能力将大幅增强。这些发现为我们提供了具体的控制手段。在准备发布 K3.1 Pro 开放权重版本时，我们从两个训练阶段均识别并移除了网络攻防相关数据，同时保留了保障模型实用性所需的通用编程任务。我们未来将在每一训练阶段持续采取适当的控制措施，网络攻防相关数据的识别与限制便是其中之一。 评估与结果。完成数据清理后，我们使用自研的 xdev-bench-hard 基准测试对 K3.1 Pro 进行了评估。该测试由专家策划，包含基于源代码的漏洞发现与利用任务，并经过校准以在当前能力水平上实现有效区分。多数任务真实复现了 Linux 内核、Node.js、JavaScriptCore、Exim 和 VirGL 等软件中近期披露的漏洞，且各项缓解措施均已启用。每项任务提供存在漏洞的源代码、简短提示以及对应的二进制文件。智能体需要开发出漏洞利用程序，在独立沙箱中实现任意代码执行，并获取密钥字符串以通过自动验证。我们报告了 pass@3 指标，未设置严格超时或输出 token 上限。 在 xdev-bench-hard 上，若中期训练和强化学习阶段均未对网络攻防相关数据进行移除或过滤，模型在 pass@3 指标上可解决 90.5% 的问题；最终版 K3.1 Pro 的得分则为 81.0%。对比表明，数据移除有效降低了漏洞研究能力，使其明显低于同一训练流程原本会产出的水平。与此同时，K3.1 Pro 仍较前代实现了大幅提升，说明即使在针对性移除相关数据后，更强的通用编程和长周期调试能力仍能泛化到此类任务上。K3.1 Pro 的网络攻防能力目前仍落后于那些已公开发布至少三个月的前沿闭源模型。我们将持续完善内部基准测试，确保在模型能力不断提升的同时，评估结果仍有参考价值。 开放权重原则。这些评估构成了我们发布开放权重版本的决策依据。首先，我们不希望发布推进网络攻防能力绝对前沿的开放权重。根据设计，K3.1 Pro 的攻击性安全能力低于原本训练流程会产出的水平，且仍低于前沿闭源模型。其次，我们计划逐步提升开放权重中可用的网络攻防能力。我们相信，开放 K3.1 Pro的权重，将更有益于出于防御目的而需要两用能力的群体。当能力强大的模型以开放形式提供，并能在用户可控的基础设施上运行时，更多团队将得以审查自身维护的代码，这其中包括那些极少接受专门安全审查的遗留系统。我们认为，让这一能力逐步扩散，而非将其集中在少数闭源系统中，最终将使所有软件变得更加安全。

    推理强度

    K3.1 Pro 始终开启思考模式，并支持通过请求顶层 reasoning_effort 配置推理强度。推理强度支持 low / high / max 三档（默认 max）。用法见 推理强度 。 
    completion = client.chat.completions.create(
    model="kimi-k3.1-pro",
    reasoning_effort="max",
    messages=[{"role": "user", "content": "证明根号 2 是无理数。"}],
)

print(completion.choices[0].message.content)
    多轮对话和工具调用时，将 API 返回的完整 assistant message 原样加入下一次请求，不要只保留 content。

    流式输出

    流式响应分别提供推理增量 reasoning_content 和最终答案增量 content。更多细节见 流式输出 。 
    stream = client.chat.completions.create(
    model="kimi-k3.1-pro",
    messages=[{"role": "user", "content": "解释为什么天空是蓝色的。"}],
    stream=True,
)

for chunk in stream:
    delta = chunk.choices[0].delta
    reasoning = getattr(delta, "reasoning_content", None)
    if reasoning:
        print(reasoning, end="", flush=True)
    if delta.content:
        print(delta.content, end="", flush=True)

    结构化输出

    使用 json_schema 和 strict: true 约束最终 message.content，只解析该字段，不解析 reasoning_content。

    姓名与年龄 schema

completion = client.chat.completions.create(
    model="kimi-k3.1-pro",
    messages=[

        "type": "json_schema",
        "json_schema": {
            "name": "person",
            "strict": True,

                "type": "object",
                "properties": {
                    "name": {"type": "string"},
                    "age": {"type": "integer"},
                },
                "required": ["name", "age"],
                "additionalProperties": False,
            },
        },
    },
)

person: dict[str, object] = json.loads(
    completion.choices[0].message.content or "{}"
)
print(person)

    自定义工具与 tool_choice

    首轮用 tool_choice="required" 强制至少调用一个工具。执行每个调用后，回传完整 assistant message，并用对应的 tool_call_id 逐条追加工具结果。

    最小天气 Agent Loop

    import json
from typing import Any

tools: list[dict[str, Any]] = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "查询城市天气",
            "parameters": {
                "type": "object",
                "properties": {"city": {"type": "string"}},
                "required": ["city"],
            },
        },
    }
]
messages: list[Any] = [
    {"role": "user", "content": "北京今天天气怎么样？"}
]

first = client.chat.completions.create(
    model="kimi-k3.1-pro",
    messages=messages,
    tools=tools,
    tool_choice="required",
)
assistant_message = first.choices[0].message
messages.append(assistant_message)

for tool_call in assistant_message.tool_calls or []:
    arguments: dict[str, str] = json.loads(tool_call.function.arguments)
    result: str = json.dumps(
        {"city": arguments["city"], "weather": "晴", "temperature_c": 24},
        ensure_ascii=False,
    )
    messages.append(
        {"role": "tool", "tool_call_id": tool_call.id, "content": result}
    )

final = client.chat.completions.create(
    model="kimi-k3.1-pro",
    messages=messages,
    tools=tools,
)
print(final.choices[0].message.content)
    详见 工具调用约束 。

    动态加载工具

    把完整工具定义放进一条不含 content 的 system message，即可从该位置起加载工具。

    from typing import Any

dynamic_messages: list[dict[str, Any]] = [
    {"role": "user", "content": "计算 23 乘以 47。"},
    {
        "role": "system",
        "tools": [
            {
                "type": "function",
                "function": {
                    "name": "calculate",
                    "description": "计算一个算术表达式",
                    "parameters": {
                        "type": "object",
                        "properties": {
                            "expression": {
                                "type": "string",
                                "description": "待计算的算术表达式",
                            }
                        },
                        "required": ["expression"],
                    },
                },
            }
        ],
    },
]
completion = client.chat.completions.create(
    model="kimi-k3.1-pro",
    messages=dynamic_messages,
)

print(completion.choices[0].message.tool_calls)

    • 声明从该 message 所在位置起生效。
    • 后续请求仍需在历史中携带该 message，服务端不会保存声明。

    1M 上下文与 TTL 缓存

    上下文缓存对普通模型请求自动生效，无需手动创建缓存：满足条件的前缀写入缓存后，命中部分按缓存命中价格计费，写入会产生一次性的缓存写入费用。TTL 支持 5m（默认）与 1h，建议按业务请求间隔选择——连续追问等间隔较短的场景用默认 5m 即可；间隔可能超过 5 分钟时，传 prompt_cache_options.ttl 选择 1h 档，避免缓存过期后重复写入。缓存按块存储，不足一整块的部分无法写入缓存，会计为缓存未命中。 
    from pathlib import Path

knowledge: str = Path("knowledge-base.md").read_text(encoding="utf-8")

for question in ["总结关键结论。", "列出三个实施风险。"]:
    completion = client.chat.completions.create(
        model="kimi-k3.1-pro",
        messages=[
            {"role": "system", "content": knowledge},
            {"role": "user", "content": question},
        ],
    )
    print(completion.choices[0].message.content)
    如何选择 TTL、提高命中率并验证用量，详见 上下文缓存 。

    官方工具

    官方工具通过 Formula 接入：
    1. 从 Formula 的 /tools 接口获取工具定义。
    2. 将定义加入 Chat Completions 请求的 tools。
    3. 收到 tool_calls 后，将对应函数名和参数提交到 Formula 的 /fibers 接口。
    4. 将完整 assistant message 和 Fiber 输出作为对应的 tool message 加入历史。
    5. 再次调用 Chat Completions，直到模型返回最终答案。
    完整客户端与接口契约见 官方工具 。联网搜索工具正在更新，近期不建议使用。

    ​
    重要限制

    • 推理强度通过请求顶层 reasoning_effort 配置，支持 low / high / max（默认 max）；K3.1 Pro 始终开启思考模式。
    • max_completion_tokens 默认 131072，最大可设置为 1048576。
    • temperature=1.0、top_p=0.95、n=1、presence_penalty=0、frequency_penalty=0 为固定值，建议不要显式传入。
    • 多轮对话和工具调用必须原样回传完整 assistant message。
    • 视觉输入不支持公网图片 URL；请使用 base64 或 ms://<file-id>，并确保 content 是对象数组。
    • 联网搜索正在更新，近期不建议用于生产流程。

    常见问题

    Kimi K3.1 Pro 如何计费？

    Kimi K3.1 Pro 上下文长度为 1M tokens，计费不按上下文长度分段，所有用量均按量付费。计费项包括：缓存写入（区分 TTL 5min / TTL 1h 两档）、输入（区分缓存命中与未命中）和输出，均按统一单价计费，详见 Kimi K3.1 Pro 定价 。

    新用户赠送的 15 元代金券可以体验 Kimi K3.1 Pro 吗？

    不可以。模型发布后，国内注册并完成认证的用户获赠的 15 元代金券不可用于体验 Kimi K3.1 Pro，请充值后解锁使用。

    Kimi K3.1 Pro 的思维链怎么关？

    目前关不了，K3.1 Pro 始终开启思考模式。如果觉得思考过程太长，可以将 reasoning_effort 设置为 low 降低推理强度，详见 推理强度。
