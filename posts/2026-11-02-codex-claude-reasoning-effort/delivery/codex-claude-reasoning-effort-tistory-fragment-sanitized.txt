<h2 id="sonnet-max-vs-opus-high">Sonnet max vs Opus high</h2>
<p>독립 평가기관 Artificial Analysis(AA)의 결과에서는 <strong>Sonnet 5.5 max가 Opus 5.5 high보다 종합 점수가 높았고, 비용은 약 2.9배 들었습니다.</strong></p>
<p>AA는 업무·코딩·과학·일반 지식 평가를 종합 지수로 묶습니다. 지수는 높을수록 좋고, 아래 비용은 각 평가 작업에 가중치를 적용한 API 비용입니다.</p>
<div class="rich-table-wrap"><table><thead><tr><th>AA v5.0 비교</th><th>Sonnet 5.5 max</th><th>Opus 5.5 high</th></tr></thead><tbody><tr><td>종합 지수</td><td>54</td><td>52</td></tr><tr><td>작업당 가중 비용</td><td>$10.02</td><td>$3.46</td></tr></tbody></table></div>
<p><a href="https://artificialanalysis.ai/models/comparisons/claude-sonnet-5-5-vs-claude-opus-5-5-high" style="color:#1a73e8;text-decoration:none;" target="_blank">AA v5.0 직접 비교</a> · Default Fallback · 2026년 11월 2일 확인.</p>
<p>토큰 단가는 Sonnet이 더 낮은데 작업 비용은 왜 더 높았을까요? AA가 집계한 Sonnet max의 가중 출력 토큰은 Opus high의 약 4.75배였습니다. 단가가 낮아도 사용하는 양이 많아지면, 한 작업에 드는 비용은 더 커질 수 있습니다.</p>
<p>코딩 평가로 좁혀 보면 결과는 조금씩 다릅니다. 실제 저장소의 코드 수정 능력을 보는 <strong>FrontierCode 2.0</strong>에서는 Sonnet max가 41.0%, Opus high가 34.5%를 기록했습니다. 기능과 코드 품질을 합친 점수로는 Sonnet 쪽이 앞섰습니다. <a href="https://cognition.com/frontiercode" style="color:#1a73e8;text-decoration:none;" target="_blank">Cognition 평가</a></p>
<p><strong>CursorBench 4.0</strong>에서는 두 설정이 55.5%와 56.0%로 비슷했습니다. Cursor도 이 정도의 작은 차이는 통계적으로 유의미하지 않을 수 있다고 설명합니다. 어떤 작업을 맡기느냐에 따라 추가 비용으로 얻는 차이가 달라질 수 있습니다. <a href="https://cursor.com/en-US/cursorbench" style="color:#1a73e8;text-decoration:none;" target="_blank">Cursor 평가</a></p>
<p>노력 단계가 바뀔 때 점수와 비용이 어떻게 움직이는지는 아래 공식 그래프에서도 볼 수 있습니다. 터미널 작업을 평가한 결과로, 각 점이 하나의 노력 단계입니다. 위로 갈수록 점수가 높고 오른쪽으로 갈수록 비용이 큽니다. <a href="https://www.anthropic.com/claude-sonnet-5-5" style="color:#1a73e8;text-decoration:none;" target="_blank">Anthropic 발표</a></p>

<h2 id="codex-단계별-차이">Codex 단계별 차이</h2>
<p>AA는 Codex에서 선택할 수 있는 <strong>GPT-6.1 Sol</strong>도 노력 단계별로 평가했습니다. <strong>high에서 max로 올렸을 때 종합 지수는 5점 높아졌고, 비용은 약 2.15배 들었습니다.</strong></p>
<div class="devlog-rich__figure" data-media-id="sol-effort" style="--rich-media-width:480px"><div class="devlog-rich__native-image devlog-rich__image">[##_Image|kage@pKr63/dJMcadcSAXK/AAAAAAAAAAAAAAAAAAAAABawnut5_Qcx5EU1NeN46atQU0-vbX2UE-edKvYaMJLt/img.png|CDM|1.3|{"originWidth":960,"originHeight":1640,"style":"alignCenter","filename":"sol-effort-v1.png","alt":"GPT-6.1 Sol의 노력을 low에서 max로 높일 때 AA 종합 지수는 35에서 55, 작업당 가중 비용은 0.16달러에서 1.27달러로 바뀌는 두 패널 도표"}_##]</div><p class="devlog-rich__caption">AA v5.0의 GPT-6.1 Sol 공개값을 재구성했습니다(2026년 11월 2일 확인). 점수와 비용은 각각 다른 눈금으로 그렸습니다.</p></div>
<p>low부터 max까지 전체를 보면 지수는 35에서 55로 높아졌고, 작업당 가중 비용은 $0.16에서 $1.27로 늘었습니다. 점수와 비용이 같은 비율로 오르지는 않습니다. 마지막 몇 점을 더 얻기 위해 얼마를 더 쓸 것인지가 선택에 들어갑니다. <a href="https://artificialanalysis.ai/models/gpt-6-1-sol-low" style="color:#1a73e8;text-decoration:none;" target="_blank">low 결과</a>, <a href="https://artificialanalysis.ai/models/comparisons/gpt-6-1-sol-medium-vs-gpt-6-1-sol-xhigh" style="color:#1a73e8;text-decoration:none;" target="_blank">medium·xhigh 비교</a>, <a href="https://artificialanalysis.ai/models/comparisons/gpt-6-1-sol-high-vs-gpt-6-1-sol" style="color:#1a73e8;text-decoration:none;" target="_blank">high·max 비교</a></p>
<p>이 결과를 보고 Codex의 설정을 바꿀 때는 모델 이름도 함께 확인하는 게 좋습니다. Power 슬라이더는 모델과 노력을 묶어 바꿀 수 있기 때문입니다. 위 비교처럼 노력만 바꿨을 때의 차이를 보려면 같은 모델을 유지해야 합니다.</p>
<p>Max와 Ultra도 작업 방식이 다릅니다. Max는 한 작업의 추론을 늘리고, Ultra는 여러 보조 에이전트로 일을 나눕니다. <a href="https://learn.chatgpt.com/docs/models?surface=app" style="color:#1a73e8;text-decoration:none;" target="_blank">Codex 모델·노력 안내</a></p>

<section class="devlog-rich__section" aria-labelledby="추론-레벨을-높일-때">
<h2 id="추론-레벨을-높일-때">추론 레벨을 높일 때</h2>
<p><strong>평소에는 기본값으로 시작하고, 빠뜨린 조건이나 해결하지 못한 오류가 있을 때 한 단계 올리는 쪽을 권합니다.</strong> 이미 원하는 결과를 얻었다면 더 높은 설정으로 다시 돌릴 필요는 적습니다.</p>
<p>기다리는 시간의 차이는 Claude Code 엔지니어 Thariq의 운동 앱 제작 사례에서 잘 드러납니다. Opus 5.5로 앱 하나를 만들게 했을 때 low는 1.5분, high는 11분, max는 67분이 걸렸습니다. 이 사례에서는 높은 설정이 더 많은 기능까지 추가했습니다. 시간 차이에는 모델이 추가로 수행한 작업도 들어 있는 것입니다. <a href="https://claude.dev/blog/spending-your-effort/" style="color:#1a73e8;text-decoration:none;" target="_blank">Spending your effort</a></p>
<p>그래서 노력을 올릴 때는 무엇을 더 해결해 주길 원하는지도 함께 정해두는 편이 좋습니다.</p>
<ul><li><strong>작은 수정·정리:</strong> 기본값으로 시작하고, 요청한 조건을 충족했는지 확인합니다.</li><li><strong>반복되는 오류·여러 파일이 얽힌 버그:</strong> 한 단계 높여 오류 재현과 회귀 테스트를 요청합니다. 앞서 실패한 테스트를 해결하는지가 기준입니다.</li><li><strong>실패 비용이 큰 작업:</strong> 높은 노력을 고려하되, 완료 조건과 수정 범위를 먼저 적습니다. 추가 시간이 필요한 검증에 쓰이도록 하는 것입니다.</li></ul>
<p>단계를 바꾼 효과가 궁금하다면 <strong>같은 모델·같은 입력·같은 도구</strong>로, 같은 초기 상태에서 비교하면 됩니다. 같은 오류가 사라졌는지, 재수정이 줄었는지를 보면 추가 시간을 쓴 보람이 있었는지 판단하기 쉽습니다.</p>
