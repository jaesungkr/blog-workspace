AI에게 코딩을 맡겼는데, 왜 더 피곤할까?

안녕하세요. dev.log입니다.

Claude Code에 로그인 오류 수정을 맡기고, 기다리는 동안 Codex에는 검색 화면을 고쳐 달라고 합니다. 잠시 뒤 한쪽에서는 “로그인 방식을 바꿔도 될까요?”, 다른 쪽에서는 “검색 버튼을 어디에 둘까요?”라는 질문이 돌아옵니다. 이럴 때는 작업마다 멈춘 지점과 내게 필요한 결정을 파일에 남기고, 답할 질문을 한곳에 모아 보세요. 어느 대화에서 무슨 결정을 했는지 매번 되짚는 일을 줄일 수 있습니다.

위 상황과 아래의 로그인 사례는 설명을 위해 만든 예시입니다. 오늘은 GeekNews에 소개된 내용을 다뤄볼까 합니다. 글쓴이 Sergey Kuhne는 여러 AI 작업을 오가며 지치는 문제를 다루면서, 작업 기록을 파일로 남기고 자신의 판단이 필요한 일을 모아 처리하는 방법을 소개했습니다.

여러 작업의 결과를 모아 한 건씩 검토하는 모습을 표현했습니다.

목차

  1. 질문이 올 때마다 대화창을 옮기던 방식에서
  2. 같은 프로젝트에 대기함을 만드는 첫 요청
  3. 작업 AI에게 질문을 남기고 기다리게 하기
  4. 로그인·검색·테스트 중 내가 답할 것만 모으기
  5. 한 건 결정한 뒤 원래 작업으로 돌려보내기
  6. 첫 도입은 두 작업과 한 번의 반환까지

질문이 올 때마다 대화창을 옮기던 방식에서

GeekNews에 소개된 Sergey Kuhne의 글은 여러 AI 작업을 오갈 때 생기는 작업 순서와 맥락의 문제를 다룹니다. 저자는 AI가 사람의 판단을 필요로 하는 일만 한곳에 모았습니다. 한 건을 읽고 결정한 뒤 다시 작업 큐에 넣으면, 그 일을 계속 기억하려고 애쓰지 않고 다음 건에 집중할 수 있다는 설명입니다. 여기서 큐는 처리할 일을 순서대로 모아 둔 목록입니다.

이 차이를 로그인·검색·테스트 작업을 함께 진행하는 가상 상황으로 비교해 보겠습니다.

전: 도착한 질문마다 바로 반응하기

로그인 담당이 “재발급 버튼을 넣을까요?”라고 묻습니다. 화면을 살피던 중 검색 담당이 새 화면을 보여 주고, 테스트 담당은 실패 로그를 보냅니다. 검색 결과와 로그를 먼저 읽다 보면, 로그인에서는 무엇을 결정하려고 했는지 다시 찾아야 합니다.

후: AI는 질문을 제출하고, 사람은 한 건씩 결정하기

로그인과 검색 담당은 필요한 질문과 판단 자료를 각자 작업 카드에 저장하고 답을 기다립니다. 사람은 검토할 때 두 질문을 모은 대기함을 엽니다. 로그인 버튼 위치를 정해 해당 작업을 재개시킨 뒤, 검색 화면을 봅니다. 이미 허용한 범위에서 원인을 조사할 수 있는 테스트 담당은 조사를 계속합니다.

아래 그림처럼 사람이 검토한 한 건은 결정과 함께 AI 작업으로 돌아갑니다. 전체 개발이 끝나기 전에도, 지금 할 판단을 마쳤다면 다음 질문으로 넘어갈 수 있습니다.

결정이 필요한 카드를 한 건씩 검토하고, 다음 행동을 기록한 뒤 추가 작업으로 돌려보내거나 완료합니다.

Kuhne의 실제 구현은 Git에 작업 상태를 저장하고, 스크립트로 판단 대기 목록을 만들며, Claude artifact에서 검토하는 구성입니다. 이 글에서는 그 처리 순서를 필요할 때 AI에게 목록 갱신을 요청하는 방식으로 줄여 적용합니다. 아래 파일 구성과 지시문은 dev.log에서 제안하는 최소 도입안입니다.

같은 프로젝트에 대기함을 만드는 첫 요청

각 작업 대화가 동일한 실제 로컬 프로젝트 폴더를 읽고 쓸 수 있어야 합니다. 읽기만 가능한 세션이라면 필요한 파일의 저장 권한부터 확인하세요. 서로 다른 클라우드 작업 공간이나 Git worktree는 파일이 자동으로 합쳐지지 않으므로 이 시작안에서는 제외합니다.

현재 프로젝트에서 대화 하나를 열고 이름을 ‘작업 검토’로 정합니다. 이 대화는 질문 목록을 대신 모아 주는 역할입니다. 다음 내용을 복사해 요청하세요.

이 프로젝트에 AI 작업의 판단 대기함을 만들어 주세요. ai-work/README.md에는 아래 운영 규칙을, ai-work/tasks/에는 빈 작업 카드 양식을, ai-work/inbox.md에는 빈 대기 목록을 만드세요. 기존 파일이 있으면 내용을 먼저 읽고 보존하세요. 지금은 제품 코드를 수정하지 마세요.

각 작업 AI는 자기 카드만 갱신합니다. 카드에는 작업 ID, 목표, 담당 대화 이름, 상태, 현재 질문, 선택지와 추천 이유, 판단 자료 경로, 최근 결정, 다음 행동, 갱신 시각을 적습니다. 상태는 ‘작업 중’, ‘판단 대기’, ‘막힘’, ‘완료’로 구분합니다.

사람의 결정이 필요한 지점에서는 질문과 자료를 저장하고 해당 작업을 멈춥니다. 이미 허용한 조사는 계속하고, 권한 부족이나 도구 오류는 ‘막힘’으로 적습니다. 배포·삭제·권한 변경은 별도 허락 없이 하지 않습니다. 비밀번호나 API 키는 기록하지 않습니다.

이 ‘작업 검토’ 대화만 inbox.md를 갱신합니다. 내가 갱신을 요청하면 각 카드를 다시 읽고 ‘판단 대기’만 짧게 모으세요. 코드 수정이나 작업 재개는 맡지 않습니다. 만든 파일의 실제 경로를 알려 주세요.

편집기에서 ai-work 폴더를 열어 세 위치를 확인합니다.

  • README.md: 모든 작업 대화에 적용할 규칙입니다.
  • tasks/: 작업별 질문, 자료, 결정을 담는 카드가 들어갑니다.
  • inbox.md: 지금 사람이 답할 질문만 모은 목록입니다.

대기함에 실제로 맡기지 않은 작업이나 가짜 완료 결과가 들어 있다면 지우도록 요청합니다. 첫 준비가 끝났을 때는 빈 대기함이 정상입니다.

작업 AI에게 질문을 남기고 기다리게 하기

각 작업 대화에 목표를 설명한 뒤 “아직 수정하지 말고, 예상 변경 파일을 먼저 알려 주세요”라고 요청합니다. 공통 컴포넌트나 전역 CSS처럼 겹치는 파일이 있으면 한 작업을 마친 뒤 다음 작업을 시작합니다.

진행할 작업에는 규칙과 카드 경로를 함께 지정합니다. README.md라는 이름만으로 모든 도구가 자동으로 읽는다고 가정하지 않습니다. 로그인 작업 대화의 이름을 ‘로그인 수정’으로 정했다면 다음처럼 시작합니다. 아래 작업 내용과 카드 경로는 실제 프로젝트에 맞게 바꾸세요.

ai-work/README.md를 먼저 읽어 주세요. 작업 ID는 T01, 담당 대화는 ‘로그인 수정’, 카드는 ai-work/tasks/T01-login.md입니다. 만료된 로그인 링크를 열면 흰 화면이 나오는 문제를 조사하고, 앞서 확인한 파일 범위와 기존 요구사항 안에서 수정해 주세요. 정상 링크의 로그인은 유지해야 합니다.

새 UI나 요구사항을 내가 선택해야 하면, 가능한 선택지와 추천 이유, 확인할 화면·변경 파일을 카드에 적고 상태를 ‘판단 대기’로 바꾼 뒤 해당 작업을 멈추세요. 채팅에는 질문 한 줄과 저장 경로를 알려 주세요. 답을 기다리며 같은 수정을 반복하지 마세요. 실행한 테스트와 실행하지 못한 항목도 구분해 적어 주세요. 다른 작업 카드와 inbox.md는 수정하지 마세요.

검색 작업은 별도 대화 ‘검색 화면’에 맡깁니다. 작업 ID와 카드 경로는 T02, ai-work/tasks/T02-search.md로 바꿉니다. 목표에는 “모바일 검색 버튼이 줄바꿈되는 원인을 고치되, 배치 변경이 필요하면 시안을 보여 주고 선택을 기다려 주세요”라고 적습니다.

이제 질문이 도착했을 때 바로 모든 대화를 읽을 필요는 없습니다. 카드가 저장됐다는 알림을 확인하고, 지금 하던 일을 마친 뒤 질문을 검토할 때 대기함을 갱신합니다. 결제 실패나 운영 장애처럼 즉시 대응해야 하는 일은 이 목록 처리 시간까지 미루지 않습니다.

로그인·검색·테스트 중 내가 답할 것만 모으기

‘작업 검토’ 대화에 아래 요청을 보냅니다.

ai-work/tasks/의 현재 카드를 다시 읽고 ai-work/inbox.md를 갱신해 주세요. ‘판단 대기’만 작업 ID, 결정할 질문, 추천안과 이유, 판단 자료·카드 경로, 답을 돌려보낼 대화 이름으로 짧게 정리하세요. 마감이 명시됐거나 다른 작업을 막는 항목을 먼저 두고, 같은 조건이면 작업 ID 순으로 정렬하세요. 우선순위 근거가 없으면 만들어 내지 마세요.

‘작업 중’과 ‘완료’는 대기 목록에서 빼고, ‘막힘’은 별도 짧은 목록으로 보여 주세요. 마지막으로 읽은 시각을 적고, 각 작업 카드와 제품 코드는 수정하지 마세요.

가상의 세 카드가 아래 상태라면, 사람이 볼 판단 대기 목록에는 로그인과 검색 두 건이 남습니다.

T01 로그인: 재발급 버튼 위치 결정

  • 질문: 만료 안내 아래에 ‘링크 다시 받기’ 버튼을 넣을까요?
  • 추천: 안내 바로 아래에 둡니다. 만료 이유를 읽고 같은 화면에서 다시 요청할 수 있습니다.
  • 확인할 것: notes/login-expired.png의 화면 시안과 T01-login.md의 변경 내용입니다.
  • 답을 전달할 곳: ‘로그인 수정’ 대화입니다.

T02 검색: 수정한 모바일 배치 승인

  • 질문: 버튼을 입력창 오른쪽에 둔 시안으로 진행할까요?
  • 추천: 오른쪽 배치를 유지합니다. 현재 시안에서는 좁은 화면에서도 버튼이 다음 줄로 내려가지 않습니다.
  • 확인할 것: notes/search-mobile.png의 시안과 T02-search.md의 확인 범위입니다.
  • 답을 전달할 곳: ‘검색 화면’ 대화입니다.

T03 테스트: 수정 전에도 실패했는지 조사 중

수정 전 상태와 로그를 비교하는 일을 이미 허용했다면 AI가 조사할 수 있습니다. 이 카드는 ‘작업 중’에 두고 판단 대기 목록에서 뺍니다. 조사 뒤 테스트를 삭제할지, 기존 동작을 바꿀지 선택해야 한다면 그때 질문을 올립니다.

위 경로와 결과는 절차를 설명하기 위한 예시입니다. 실제 카드에는 존재하는 자료만 적고, 미확인 화면이나 테스트는 그대로 ‘미확인’이라고 표시해야 합니다. 검토할 자료가 빠져 있으면 해당 작업 대화에 자료 보완을 요청한 뒤 다음 카드를 봅니다.

한 건 결정한 뒤 원래 작업으로 돌려보내기

로그인부터 본다면 카드가 가리키는 시안을 열고 버튼 위치를 결정합니다. 그 결정을 ‘로그인 수정’ 대화에 직접 전달합니다.

ai-work/tasks/T01-login.md를 읽고 이어서 진행해 주세요. ‘링크 다시 받기’ 버튼은 만료 안내 바로 아래에 넣는 것으로 결정했습니다. 이 결정을 카드에 기록하고 상태를 ‘작업 중’으로 바꾼 뒤 수정하세요. 만료된 링크와 정상 링크를 각각 확인하고 결과 위치를 남겨 주세요. 내가 결과를 확인해야 할 때 다시 ‘판단 대기’로 올리고, 배포하지 마세요.

작업 AI가 결정 수신과 카드 갱신을 확인하면, ‘작업 검토’ 대화에 대기함을 다시 갱신해 달라고 요청합니다. T01이 ‘작업 중’이라면 방금 답한 버튼 위치 질문은 빠지고 T02 검색이 남습니다. T01에서 새 결과 검토를 요청했다면 이전 질문을 반복한 것인지, 새 결과를 확인해 달라는 것인지 구분합니다. 로그인 코드 구현이 계속되는 동안 사람은 검색 시안 한 건에 집중할 수 있습니다.

검색도 같은 방식입니다. 시안을 보고 승인한다면 ‘검색 화면’ 대화에 “T02의 오른쪽 버튼 배치로 진행하고, 작은 화면에서 입력창과 버튼이 잘리지 않는지 확인해 주세요”라고 전달합니다. 자료가 부족하거나 다른 배치를 원하면 필요한 보완을 구체적으로 돌려보냅니다.

inbox.md에 답만 써 놓아도 다른 대화가 저절로 깨어나지는 않습니다. 이 시작안에서는 결정을 원래 대화에 전달하고, 작업 AI가 카드를 갱신한 뒤 목록을 다시 만드는 것까지 사람이 지시합니다. 새 대화로 이어갈 때도 카드 경로를 지정해 먼저 읽게 합니다.

첫 도입은 두 작업과 한 번의 반환까지

이 방식을 적용했는지는 파일 개수보다 실제 처리 결과로 확인할 수 있습니다. 로그인 결정을 전달한 뒤에는 다음 세 상태가 맞아야 합니다.

  1. T01 카드에 방금 내린 결정이 남고, 작업이 재개됐습니다.
  2. 새로 갱신한 대기함에서 방금 답한 버튼 위치 질문이 해소됐습니다. 새 질문이 있다면 그 내용이 구별됩니다.
  3. 검색 질문과 판단 자료는 그대로 남아 있어 다음으로 검토할 수 있습니다.
